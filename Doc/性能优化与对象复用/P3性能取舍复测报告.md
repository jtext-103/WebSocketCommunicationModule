> 后续纯分析已完成，产品代码未改；发现 Status 构造时机改变，GC／CPU 影响尚未隔离。详见 [最新原因分析](P3重嵌套耗时原因分析.md)。

## 结论

分配收益可重复。默认运行时下，8 个复杂嵌套字段的固定输入再次出现小幅耗时增加，不能再只将初次 +4.2% 视为未复现信号。完整 APP 两轮 CPU／次发布均下降，但幅度从约 9.0% 变为 1.7%；平均 RTT 方向改变。分钟 P99 中位数两轮分别增加约 0.216 ms 和 0.105 ms。数据支持存在取舍，仍不足以证明尾延迟由 P3 导致或保证稳定整体收益。

按用户“遇到问题停止让我确认”的要求，复测结束后停止继续修改和追加压测，保留所有数据。建议先分析默认运行时下重嵌套路径的额外耗时，再决定是否优化或接受该取舍；本次没有实施新的性能修改。

## Context：独立进程与反向顺序

复用原有已编译 probe 和两版冻结 DLL，无重新构建。每进程七组输入先做输出兼容检查，每组两版各预热 5,000 次，再三轮交替各 20,000 条。三进程沿用默认运行时；两进程仅在该子进程关闭 TieredCompilation，用于敏感性诊断，未改变 APP 配置，也未与默认数据合并。

重嵌套场景各进程的三轮中位数如下；CPU 为进程累计 CPU，墙钟为实际经过时间，表中耗时单位 ms／20,000 条：

| 进程／模式 | 顺序 | P2 CPU | P3 CPU | CPU 变化 | 墙钟变化 |
|---|---|---:|---:|---:|---:|
| default-01 | P2 先加载 | 750.000 | 765.625 | +2.1% | +3.3% |
| default-02-reversed | P3 先加载 | 703.125 | 750.000 | +6.7% | +3.8% |
| default-03 | P2 先加载 | 750.000 | 781.250 | +4.2% | +5.9% |
| no-tiering-01 | P2 先加载 | 1437.500 | 1296.875 | -9.8% | -9.3% |
| no-tiering-02-reversed | P3 先加载 | 1156.250 | 1156.250 | +0.0% | +1.8% |

默认设置三进程中，CPU 增加 2.1%～6.7%，配对变化中位数 +4.2%；墙钟增加 3.3%～5.9%，配对变化中位数 +3.8%。这说明在该固定输入及本机默认设置下，耗时取舍能重复。关闭分层编译后方向不一致且绝对时间明显变化，只能说明结果对运行时条件敏感，不能据此认定 JIT 是唯一原因，更不能用该诊断模式代替正常 APP 结果。

五进程的七组输出兼容检查均通过。普通 benchmark Context 每条约减少 464 B，重嵌套约减少 992 B；开头 `$id` 的兼容路径分配相同。默认设置的 benchmark Context CPU 配对变化为 −5.3%～+5.6%，中位数 0%；64 标量 Context 也无一致 CPU 增幅。空 Context 是每进程首场景，仍有明显初始化与分层编译扰动，其大比例时间变化不当作稳定性能证据。小标量等短场景的 CPU 计时粒度较粗，结果和墙钟变化均保留在原始数据，未选择性删除。
