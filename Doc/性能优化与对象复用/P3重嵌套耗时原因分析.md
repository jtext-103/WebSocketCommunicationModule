# P3 重嵌套耗时原因分析

2026 年 10 月 19 日。用户选择“保留 P3，先分析重嵌套耗时原因，不改代码”后完成本次分析。P2/P3 产品与测试源码、冻结运行包均保持原哈希，未构建或运行新的 APP 压测；只用已有已编译 probe 做了两次短时采样。

## 结论与确定程度

已经解释分配下降为何不必然带来重嵌套耗时下降：P3 省去的是外层普通字典及复制，复杂值的 JSON 树转换仍然存在。默认设置下该固定输入的小幅耗时取舍可以重复，但目前仍不能把额外约 1～2 μs 精确归因到某个函数，尤其不能直接认定“文化比较器变重”或“JIT 导致全部回退”。

未发现 P3 新增重锁、递归扫描 Context 树或在正常唯一键输入下反复清空并重建字典。还确认了一处构造顺序差异：P3 提前构造 Status，使其默认 Context 在转换期间仍被持有。这是优先值得隔离的变量；实际 GC 与 CPU 影响未测定，尚不是已证实的单一根因。字典写入路径和运行时编译条件也仍待分离。

## 先明确增量有多大

以下沿用无采样器的默认运行时复测结果，每个独立进程各三轮 20,000 条，取进程内三轮中位数；CPU 为整个进程的累计 CPU，不是单函数 CPU。每条数值由固定消息数换算。

| 进程 | P2 CPU，μs／条 | P3 CPU，μs／条 | 增加，μs／条 | 增幅 |
|---|---:|---:|---:|---:|
| default-01 | 37.500 | 38.281 | 0.781 | +2.1% |
| default-02-reversed | 35.156 | 37.500 | 2.344 | +6.7% |
| default-03 | 37.500 | 39.062 | 1.562 | +4.2% |

分配约 50,394→49,402 B／条，减少 992 B（约 2.0%）。这是包含初始 JSON 解析、Context 转换、Sample 和事件构造的完整 DeserializeMessage，不是 Context 函数的独占成本。P3 剩余约 49 KB 不能全部归于嵌套树，也不能以分配字节比例计算 CPU 比例。

## 两版实际路径

| 步骤 | P2 | P3 普通 Context |
|---|---|---|
| 解析消息字符串 | JObject.Parse 创建初始树 | 相同 |
| 读取 Context | ToObject 创建普通字典并转换各值 | 创建最终文化规则字典，Populate 转换各值 |
| 嵌套 object／array 值 | Json.NET 读取 token 并产生结果值树 | 同类 Json.NET 转换仍然执行 |
| 构造最终外层字典 | 从普通字典复制并使用 InvariantCultureIgnoreCase | 转换过程中直接写入最终字典 |
| Status 默认初始化 | Context 转换完成后才构造 | 对象初始化先构造 Status，再计算 Context 右值 |

Json.NET 对未指定具体类型的嵌套对象会使用 JTokenWriter 构建结果对象，数组也有相应 token 转换路径。P3 没有改为直接返回原来的子树，所以不能期望复杂值转换成本随外层字典一起消失。这解释收益边界，尚不能单独解释 P3 为何多出几个百分点。[Json.NET 13.0.4 实现](https://github.com/JamesNK/Newtonsoft.Json/blob/13.0.4/Src/Newtonsoft.Json/Serialization/JsonSerializerInternalReader.cs#L259)

## 已确认的构造时机差异

P2 先用局部变量接住完成转换的 Context，再构造 Status。P3 则将 DeserializeContext 放进对象初始化器的属性右值。C# 先完成构造函数，再执行属性初始化；因此调用顺序确实发生改变。[微软对对象初始化器的说明](https://devblogs.microsoft.com/dotnet/c-9-0-on-the-record/)

```text
P2：转换 Context → 构造 Status（创建默认 Context）→ 替换默认 Context
P3：构造 Status（创建默认 Context）→ 转换 Context → 替换默认 Context
```

SampleBase 的 Context 属性初始化器会分配字典；默认构造设置资源类型、路径、远端标记和值，Status 构造再设置自身资源类型。P3 的 Status 对象在 helper 执行期间需要保留，其默认 Context 尚未被替换。因此该临时对象图的持有期覆盖了复杂转换，而 P2 没有这段覆盖。较多嵌套分配可能让其跨越 GC、改变存活／晋升和内存布局；这是推断，尚未取得该对象的存活／晋升证据，也未量化对 4.2% 的贡献。不能仅凭顺序差异认定 GC 已经解释全部差额。

源码位置：[P3 返回表达式](../../WebSocketCommunicationModule/Protocol/WebSocketMessageSerializer.cs#L204)、[SampleBase 默认构造](仓库外引用索引.md#e057)、[Status 默认构造](仓库外引用索引.md#e058)。Core 构造函数未改动，差异来自 WS 调用顺序。

后续可以把 Context 转换结果先存入局部变量，再构造 Status，以恢复原有时机，同时保留 P3 的外层字典分配收益。这只是待验证方案，本次没有修改或运行该版本。该实验比同时改比较器、解析器或 Core 构造接口更容易判断原因；若顺序恢复后差额仍在，再分离字典写入和 JIT。

## 逐项判断

| 怀疑点 | 结论 | 依据与限制 |
|---|---|---|
| 新增重锁同步 | 当前没有相应证据 | P3 修改未新增 lock；两次单线程受控采样的 Monitor contention 记录均为 0。不能据此排除完整 APP 的其他锁等待 |
| 元数据深度扫描 | 可以排除为该实现的原因 | HasLeadingContextMetadata 只检查 First 属性，现行版本没有遍历嵌套树 |
| 冲突检查重复构造字典 | 正常输入不进入该分支 | 固定场景为 item0～item7 唯一键，数量相等；Clear/Add 只在键合并的错误分支执行 |
| 比较器改变 | 规则未改变 | 两版最终字典都使用 InvariantCultureIgnoreCase，P3 只改变其参与写入的阶段 |
| 写入调用路径 | 确有变化，差额未分离 | P2 先普通字典再 AddRange；P3 在 PopulateDictionary 中经 IDictionary 索引器写入最终字典。不同调用形态可能影响代码生成，但不能仅凭接口调用就认定更慢 |
| Status 构造时机 | 提前构造已确认，成本影响未证明 | 默认 Context 在转换期间仍被持有；是否实际增加晋升或 CPU 尚未隔离 |
| JIT／PGO | 有敏感性，因果未证明 | 默认设置的增量重复；关闭分层编译后方向不一致且绝对时间改变。当前未得到具体方法编译版本与增量的对等证据 |
| GC | 分配下降不保证计时窗口等比例受益 | GC 时机、进程 CPU 和壁钟不同；不能拿暂停总量直接替代函数 CPU 或 RTT |

特别是文化哈希：.NET 10 的 Dictionary 从另一字典构造时会检查比较器；比较器不同需要重新加入各键。P2 的临时字典与最终字典比较器不同，因此 P2 也要付这份文化规则哈希成本。索引器写入与 Add 最终均进入 TryInsert，只是重复键策略不同。不能把 P3 采到 ICU 哈希就解释为新增了全部哈希开销。[.NET 10.0.12 Dictionary 实现](https://github.com/dotnet/runtime/blob/v10.0.12/src/libraries/System.Private.CoreLib/src/System/Collections/Generic/Dictionary.cs#L101)

## 新采样能证明什么

两次使用 dotnet-sampled-thread-time 与 dotnet-common，顺序分别为 P2→P3、P3→P2；已有 probe 每次仍执行七组输入。它们仅用于检查调用路径，采样期间的耗时不用于替代此前无采样器的性能比较。

两份 trace 事件丢失均为 0。调用栈能看到 JSON 读取、PopulateDictionary、P3 的 DeserializeContext、文化哈希及 P2 的字典复制路径。但大量叶样本落在 PollGC 和 ICU 原生调用边界；这是线程时间采样，存在安全点与原生边界偏差，不能转写成各函数精确 CPU 百分比。PollGC 叶样本也不全等于实际 GC 暂停。

尝试按 stdout 收到时间与每轮 elapsed 切分重嵌套区间后，程序集一致性校验未通过，故该切分结果明确标记为拒绝用于版本耗时归因。输出传递延迟、时间对齐和同名模块识别都可能影响该办法，具体来源没有继续隔离。原始数据保留，不选择性删除；不引用这些窗口的逐版本比例。

当前采集设置没有取得所选 MethodLoadVerbose 的逐方法版本记录。该缺失不表示未发生 JIT，也不能据此证明某个方法一直处于 Tier 0。全局 TieredCompilation 活动不足以把 4.2% 归因到具体方法。

## 建议的下一步与本次边界

下一步先用只恢复 Status 构造时机的独立诊断版本隔离该变量；若仍有差额，再独立测量预解析 Context 的转换阶段，把“初始 JObject.Parse”和“字典／嵌套值转换”分开；固定外层键数量，只改变复杂值大小，以判断差额是否随嵌套量增长。两版应使用相同入口和预热条件，保留无采样器数值对照，再对慢阶段取方法版本与调用栈。该分段诊断尚未实施，当前也未新增诊断项目。

若证据指向嵌套树重建，后续方案才评估减少再次物化；复用既有 JToken 或改成按成员转换可能改变可变对象所有权、保留元数据和引用语义，需要沿用 P3 的兼容边界验证。若差额只在写入／JIT 阶段，则围绕该路径做小范围优化，避免扩大修改范围。当前没有足够依据将比较器改为 OrdinalIgnoreCase、全局关闭分层编译，或为 Context 增加共享字典池。

本次分析完成，保留 P3；P3 整体性能验收仍待决定，不宣称已定位全部额外 CPU 或保证吞吐／尾延迟改善。没有进一步改动产品、重跑功能测试、发布服务器包或执行回退。
