# CFET 性能优化与对象复用修改方案

日期：2026 年 10 月 19 日。状态：P2 本机阶段完成，P3 兼容性及分配通过，整体性能验收待确认。用户选择保留 P3 仅分析后，已完成源码与两次短时采样分析，产品代码未改。确认 P3 只减少外层字典，嵌套 JSON 转换仍保留；另确认 Status 从 Context 转换后构造变为转换前构造，默认 Context 因而在转换期间仍被持有，实际 GC／CPU 贡献尚未验证。重嵌套额外 CPU 约 0.8～2.3 μs／条的精确根因尚未完全隔离；未将线程时间采样误当 CPU 百分比。建议后续优先隔离构造时机，不自动修改。详见 [P3 重嵌套耗时原因分析](P3重嵌套耗时原因分析.md) 和 [分阶段交付记录](分阶段交付记录.md)。

优先通过复用 WebSocket 接收缓冲区、减少消息拼接复制、减少 JSON 中间转换降低分配。第一轮保持协议、订阅配置和事件语义不变，每完成一个阶段分别验证收益。Core 锁结构、全局对象池和消息协议重写放在后续按证据评估。

本方案说明具体修改位置、所有权和归还时机、兼容边界、实施顺序及验收方法。实施前先处理压测回包的正确性验证，随后建立新旧版本都使用的统一测量基线。

## 1 性能依据与收益边界

依据包括 [本机性能分析报告](仓库外引用索引.md#e052)、[采样解析数据](仓库外引用索引.md#e051) 和 [服务器 24 小时对比报告](仓库外引用索引.md#e050)。

| 观察 | 支持的修改方向 | 解释边界 |
|---|---|---|
| 接收器每次创建 64 KiB 数组，四个 APP 均采到指向接收器的 65560 字节数组对象 | 复用接收临时数组 | 65560 字节含对象开销；数组池预热和未命中时仍可能分配 |
| 接收器每次创建 MemoryStream，再调用 ToArray 和 UTF8 解码 | 单帧直接解码，分片减少一次复制 | 返回字符串仍需要独立存储，第一轮不追求零分配 |
| JSON 解析及 Sample 转换出现在业务调用栈中 | 减少 JObject、字典及字符串之间的转换 | 包含调用栈会重叠，样本数不能当作 CPU 百分比 |
| Context 转换先创建普通字典，再复制为忽略大小写字典；存在文化规则哈希采样 | 减少字典构造、复制和重复查找 | 比较器规则影响兼容性，第一轮保持原规则 |
| 60 秒采样中，各 APP 的 Monitor 累计竞争等待约 29 至 118 ms | 接收和转换先于大范围改锁 | 采样主要覆盖前半段，不能排除后半段等待增加 |

本机采样运行在 Windows 和 .NET 10.0.12；服务器为 Linux 和 .NET 10.0.13。新旧实现应分别在相同系统、运行时和负载下比较，不能直接用两台机器的数值判断优化收益。

本机后半段平均 RTT 从前两分钟的约 1.5 至 2.1 ms 升至第 5 分钟约 16.5 ms，该慢阶段尚未定位。减少分配是已找到的优化机会，不代表已经解释这段延迟恶化。已采样窗口的 GC 暂停也不足以支持按相同比例预测 RTT 改善。

### 1.1 接收数组分配量估算

往返模式下，假设总发布速率为每秒 100 次、每个从节点收到一个 Tick 并发送一个 Echo，仅数据消息接收次数近似为：

```text
接收消息数每秒 = 2 × 从节点数 × 发布次数每秒
接收数组分配字节每秒 = 接收消息数每秒 × 65536
```

| 配置 | 理论数据消息接收次数 | 原实现接收数组分配量 |
|---|---:|---:|
| 4 APP，3 个从节点 | 600 次每秒 | 37.5 MiB 每秒 |
| 6 APP，5 个从节点 | 1000 次每秒 | 62.5 MiB 每秒 |

这是理想发布速率下的估算，不是本机实际测得的可节省量；不含握手、心跳、JSON 对象和消息拼接。8 B 是业务载荷大小，线上消息还包含 JSON 字段和事件元数据。1000 种事件共享总发布频率，并非每种事件都按每秒 100 次发布。

## 2 实施顺序与修改范围

| 阶段 | 内容 | 范围 | 主要验收点 |
|---|---|---|---|
| Q0 | 验证并消除压测共享 Echo 回读竞态，冻结测量版本 | Benchmark Thing 和相关测试 | 并发回包携带对应的 Seq，形成可信对照基线 |
| P1 | 接收临时数组改为租借与归还 | WS 公共接收器 | 稳定小消息接收不再固定新建 64 KiB 数组 |
| P2 | 单帧直接解码，分片解码移除 ToArray | WS 公共接收器 | 普通单帧不创建 MemoryStream，分片保持原语义 |
| P3 | 一次构造最终 Context，减少 JSON 中间转换 | WS 反序列化；Benchmark 转换单独评估 | 字段、类型和错误处理兼容，字典及字符串分配下降 |
| P4 | 评估发送端流式编码与缓冲区租借 | WS 序列化、Session 和客户端发送入口 | 仅在后续采样证明发送分配值得处理时实施 |
| P5 | 评估单订阅者直接扇出和其他调度开销 | WS 扇出队列 | 保留队列边界、取消检查及多订阅者并发 |

Q0 属于测量正确性。P1 和 P2 是建议优先落地的产品优化；P3 在它们通过回归和性能对照后实施。P4、P5 不与首轮混合修改，以便判断各阶段收益。

首轮保留 ReceiveBufferSize 默认 64 KiB、MaxMessageBytes 默认 4 MiB、PerformanceLevel、发布间隔、重订阅间隔、队列容量和并发上限。减少分配通过复用和减少转换实现，不通过改变测试负载或丢弃消息实现。

## 3 对象复用的所有权规则

复用的关键是对象最后一次使用何时结束。临时接收数组可在解码完成后归还；已发布事件可能仍在队列中或被回调持有，不能按发布函数返回时机回收。

| 对象 | 所有者 | 可采用的方式 | 释放或归还时机 |
|---|---|---|---|
| 接收临时 byte 数组 | 一次 ReceiveTextAsync 调用 | 从 ArrayPool 租借 | 全部异步接收及解码完成后，在 finally 中归还 |
| 分片消息拼接区 | 当前消息接收调用 | 首轮保留局部 MemoryStream | 最终解码完成或异常退出时释放 |
| 已解码字符串 | 返回值及解析调用方 | 独立字符串，不池化 | 由 GC 管理 |
| JObject 和解析后载荷 | 当前消息和后续事件 | 减少创建，不主动回收重用 | 引用全部结束后由 GC 管理 |
| Sample、Context、EventArg、Tick 和 Echo | 事件发布链与消费者 | 每条事件保持独立状态 | 首轮不放入对象池 |
| 发送缓冲区 | 一次完整发送操作 | 后续可采用显式租借对象 | 等待发送锁及 SendAsync 全部结束后归还 |
| ContractResolver 和只读配置 | 序列化模块 | 继续复用现有缓存 | 跟随模块或进程生命周期 |

ArrayPool 可能返回比请求更大的数组，且内容不保证清零。使用时只暴露指定接收范围，只读取实际收到的字节数；归还后不再读取或保存其 Memory、Span 或 ArraySegment 引用。每次租借只能归还一次。[Rent 约定](https://learn.microsoft.com/en-us/dotnet/api/system.buffers.arraypool-1.rent?view=net-10.0) 和 [Return 约定](https://learn.microsoft.com/en-us/dotnet/api/system.buffers.arraypool-1.return?view=net-10.0) 是实现依据。

数组池降低分配速率，但可能保留数组供后续使用，因此分配下降不必然对应 Working Set 下降。验收同时观察活动租借数量和稳定内存，避免只看 GC 指标。

已经初始化且后续不修改的只读载荷内容可以继续共享；需要避免的是将仍被事件引用的数组改写为下一条消息的内容。复用临时接收区与复用已发布载荷具有不同的生命周期。

## 4 P1 接收临时数组复用

### 4.1 修改入口

修改 [WebSocketMessageReceiver.ReceiveTextAsync](../../WebSocketCommunicationModule/Protocol/WebSocketMessageReceiver.cs#L10)。客户端的 [接收调用入口](../../WebSocketCommunicationModule/Client/RemoteEndpointConnection.cs#L732) 和服务端的 [接收调用入口](../../WebSocketCommunicationModule/Server/WebSocketSession.cs#L351) 已复用该方法，因此应在公共接收器完成首轮优化。

第一阶段保持 Task<string> 返回类型和调用接口。将 new byte[bufferSize] 改为 ArrayPool<byte>.Shared.Rent，并把原有接收、拼接、拒绝和解码逻辑放入同一个 try/finally。

以下仅表达租借范围，不能替代完整接收实现：

```csharp
var pool = ArrayPool<byte>.Shared;
var buffer = pool.Rent(bufferSize);
try
{
    // 接收操作只使用 new ArraySegment<byte>(buffer, 0, bufferSize)。
    // 每次 await ReceiveAsync 完成后，只读取 result.Count 个字节。
    // 在此完成分片排空、拼接与字符串解码。
    // 返回字符串独立持有内容，不引用租借数组。
}
finally
{
    pool.Return(buffer, clearArray: false);
}
```

首轮保持现有 ArraySegment 接收重载，减少同时变化的行为；Memory<byte> 接收重载可在后续独立评估。实际接收长度使用配置的 bufferSize，不能直接使用租借数组的 Length，否则池返回更大数组时会改变分片行为。

接收器只读取有效字节范围，返回值为独立字符串，因此该路径无需依赖租借数组原本是否清零。若部署的数据处理要求归还前清除内容，则应使用 clearArray: true，并将清除成本纳入该部署的性能对照。

### 4.2 为何首轮按调用租借

按调用租借能直接覆盖正常返回、格式错误、关闭、超时和取消路径，也不需要改变握手与重连生命周期。池中的数组可以被后续接收调用再次借用，实现复用。

按连接长期持有数组可进一步减少 Rent 和 Return 调用，但需要管理握手交接、旧连接 generation 退出与新连接启动。只有在池操作本身成为可见开销时再评估。即使按连接复用，也应由对应接收循环在 finally 中归还，不能由 Dispose 线程提前归还仍在异步 I/O 中的数组。

同一个 WebSocket 的接收继续串行执行。官方约定同一 WebSocket 同时只支持一个接收操作；不同连接的接收使用各自独占的租借数组。[ReceiveAsync 约定](https://learn.microsoft.com/en-us/dotnet/api/system.net.websockets.websocket.receiveasync?view=net-10.0)

### 4.3 必须保留的接收行为

- 成功接收、Close、异常、取消和超时均归还数组；归还发生在异步操作结束之后。
- 二进制消息和超长消息按现有行为拒绝；分片消息被拒绝后继续读取至 EndOfMessage，且不再拼接被拒绝的内容。
- 已拒绝消息的后续片段继续使用固定接收区，不为排空而扩容。
- 保留当前关闭异常和上层错误处理分类；不得因池化改成静默接受或提前返回半条消息。
- 不使用共享静态 byte 数组，不让其他连接覆盖仍在处理的消息。

## 5 P2 减少拼接与复制

### 5.1 单帧直接解码

接收第一段后，如果消息类型为 Text、EndOfMessage 为 true，且字节数符合 MaxMessageBytes，直接调用 Encoding.UTF8.GetString(buffer, 0, count)，随后归还数组并返回字符串。

该常见路径不再创建 MemoryStream，也不再将消息复制到拼接区和 ToArray 结果。只有需要跨段累积的消息才创建拼接区。空文本消息仍解码为空字符串，由现有协议解析层决定是否拒绝。

大小检查必须先于成功返回。不能因单帧直接返回而绕过 MaxMessageBytes；接收缓冲区大小与消息最大长度是两个独立限制。

### 5.2 分片路径移除 ToArray

首轮保留局部 MemoryStream 拼接分片，通过 TryGetBuffer 取得有效区，在 stream 释放前直接对实际长度解码，避免 ToArray 再创建一份完整消息数组。必须使用实际偏移和 Length，不能解码 Capacity 或租借数组的全部内容。

UTF8 字符可能跨片段，分片消息应拼接完成后统一解码。第一轮保持现有 Encoding.UTF8 的处理策略，不同时引入严格 UTF8 拒绝规则或每段独立解码。

### 5.3 分片拼接区的进一步复用

仅当后续负载证明分片拼接仍占明显分配量时，再用具有 Length、Capacity 和 Dispose 的池化累积器替代 MemoryStream。增长前检查消息总长度及整数溢出；新数组接管内容后才归还旧数组；解码结束后归还最后一块数组。

不得在每次接收开始时租借 MaxMessageBytes 大小的数组。默认上限 4 MiB 只是允许的消息长度，通常的小消息不应为此长期占用 4 MiB。若以后按连接缓存拼接区，应设定明确的保留上限；ArrayPool.Shared.Return 不保证大数组立即释放，不能用它代替缓存上限设计。

## 6 P3 减少 JSON 和 Context 分配

### 6.1 直接构造最终 Context

[DeserializeSample](../../WebSocketCommunicationModule/Protocol/WebSocketMessageSerializer.cs#L192) 修改前先将 context 转为普通字典，再复制到 InvariantCultureIgnoreCase 字典。与此同时，Status<object> 默认构造会创建随后被替换的默认 Context。

实际实施仅修改 WS 转换：普通 Context 预分配使用现有比较器的最终字典，由原有 JsonSerializer.Populate 通过局部 JTokenReader 填充，减少一份临时字典及整表复制，随后仍沿用 Status<object> 默认初始化后赋值 Context。默认 Status 初始化成本保留，Core 构造接口保持原样。

开头为 `$id`、`$ref`、`$type`、`$values` 或 `$value` 的 Context 沿用旧完整转换及字典复制路径，保留 Json.NET 元数据处理及引用作用域；这些兼容输入不承诺分配下降。普通分支的 Populate 会覆盖等价键，因此用成员计数差异检测冲突，仅在错误路径重现 Add 的异常分类。嵌套对象仍在同一 reader 作用域处理，无逐值手工转换，也不扫描整棵树。

必须保持以下兼容条件：

1. 保留 StringComparer.InvariantCultureIgnoreCase，以及原来的大小写冲突处理；直接赋值覆盖键可能改变现有冲突失败行为，不能无验证替代。
2. 嵌套对象、数组、null、数值和日期保持原有 Json.NET 转换语义；不要把 JObject 自动改成自定义 Dictionary，或改变整数精度。
3. 完整保留原始 Context 元数据，包括未知扩展键、有效性、错误信息、来源路径、远端标记、资源类型和时间戳。
4. 保留 context 缺失时对 objectVal、val 和旧消息形式的回退兼容。
5. 每条消息拥有独立 Context。接收临时字典不得在事件发布后 Clear 再复用。

不能直接用现有 Status<object>(context) 构造函数替换当前代码来声称完成优化：该构造链仍会复制字典，并设置资源类型，可能改变比较器或原始元数据。如果后续确需消除默认 Context 初始化，应把 Core 的构造入口设计作为独立变更处理，并明确字典所有权和元数据保留规则。



已完成的纯分析还发现：当前对象初始化表达式会在 DeserializeContext 前构造 Status，而原实现先得到转换结果再构造。默认 Context 的持有期因此覆盖转换阶段，可能影响 GC 或布局，但实际 CPU 贡献未证实。后续可先隔离该顺序差异；本次没有实施此项修改。详见 [重嵌套原因分析](P3重嵌套耗时原因分析.md)。

### 6.2 减少载荷的字符串往返

[Benchmark ConvertValue](仓库外引用索引.md#e055) 对非目标类型值执行 SerializeObject 再 DeserializeObject。可单独评估：已经是目标类型时直接使用；值为 JToken 时直接转换为目标类型；其他输入保留兼容回退。

该项属于压测程序开销，不能计作 Core 或 WS 产品优化收益。若采用，应同时用于各对照版本，并重新建立统一基线；不能把新旧版本使用不同转换器的结果直接比较。转换前后核对 RunId、Seq、EventIndex、BucketIndex、时间戳和载荷内容。

Level 1 的当前转换中，valueToken 被分别转换给 Value 和 Sample。可评估只转换一次，但要先确认两个可变值共享引用是否满足事件接口约定；首轮不把引用关系变化混入 Context 优化。

### 6.3 解析器和比较器的后续边界

现有 JsonSerializerSettings 和 ContractResolver 已复用。后续若继续减少 JObject 中间树，可以评估用 JsonTextReader 直接读取协议字段，但需完整保留协议验证和旧格式兼容。Json.NET 官方也将减少中间字符串、采用流式读写列为优化方向。[Json.NET 性能说明](https://www.newtonsoft.com/json/help/html/performance.htm)

共享配置和契约缓存不代表可以并发复用任意 JsonSerializer、JsonReader 或 JsonWriter。实施时应检查已有静态 JsonSerializer 的并发使用路径；新增转换不得仅为减少实例数而扩大可变实例共享。每次转换的 reader、writer 和运行状态保持独立。

采样中的文化规则哈希支持继续评估固定协议键的查找成本，但第一轮不把比较器改成 OrdinalIgnoreCase。若以后调整，应单独验证 Unicode 键等价、路径和事件匹配语义，不能对所有字典做全局替换。[字符串比较规则](https://learn.microsoft.com/en-us/dotnet/standard/base-types/best-practices-strings)

## 7 Q0 压测回包正确性

[OnTickReceived](仓库外引用索引.md#e054) 当前创建对象后赋给共享 Echo 属性，再从 Echo 属性读取发布参数。并发处理 A、B 两个 Tick 时，A 的发布参数可能读取到 B 覆盖后的对象。

修改方向是使用局部变量保存本次新建的 Echo，属性用于展示最新值，Publish 参数直接使用该局部变量。每个回包仍新建独立对象，不能改成重用同一个 Echo 实例并反复修改 Seq。

先通过可控并发验证本次回包与输入 Seq 的对应关系，再建立同一 Q0 版本上的性能基线。历史本机测试缺失 69、重复 69 的现象与该竞态相容，但并未证明所有历史异常均由此导致；修正后仍需检查缺失、重复和乱序。

Benchmark 的转换优化与 Q0 正确性修改分开记录。Q0 后的未优化产品版本，才是 P1 至 P3 的主要对照版本；原始版本记录继续保留供历史追溯。

## 8 后续发送端复用与调度优化

### 8.1 发送端编码复用

[SerializeToUtf8Bytes](../../WebSocketCommunicationModule/Protocol/WebSocketMessageSerializer.cs#L23) 当前先生成完整 JSON 字符串，再分配 UTF8 byte 数组。后续可评估 JsonTextWriter 配合流式 UTF8 编码写入可增长缓冲区，减少完整 UTF16 中间字符串；收益应由发送端分配采样决定。

如果最终发送数组也租借，必须让一次发送操作持有缓冲区所有权，覆盖序列化完成、等待发送锁、检查订阅有效性以及 SendAsync 完成或失败的全过程。只发送 Length 范围，不发送池数组的全部容量。

现有 [发送路径](../../WebSocketCommunicationModule/Server/WebSocketSession.cs#L237) 中，等待发送锁计入发送超时。重构须保留该超时边界、取消来源和有效性复查。缓冲区不能在异步发送尚未结束时提前归还，也不能由序列化帮助方法返回前自行归还。

首轮发送端仍保留每条消息独立的最终 byte 数组。后续租借对象应具备单一归还责任，异常、取消及重复 Dispose 不得重复归还。发送受阻时需统计同时持有的数组总容量，防止分配减少却增大稳定内存。

不同订阅者的 TokenId、PerformanceLevel 可能不同，不能跨订阅者缓存并重用完整网络帧。跨消息缓存可变 EventArg、Sample、Context 或载荷也不在首轮范围。

### 8.2 单订阅者扇出

[FanOutAsync](../../WebSocketCommunicationModule/Server/Subscriptions/WebSocketSubscriptionManager.FanOut.cs#L99) 对所有数量的订阅者都使用 Parallel.ForEachAsync。后续可在只有一个订阅者时直接 await 发送，多个订阅者仍使用现有并发路径。

该优化保留有界队列、固定消费者数量、订阅有效性复查、异常隔离和取消语义。Core 对任意业务回调的 Task.Run 隔离不随此变更调整。Linked CancellationTokenSource、锁和队列对象的池化也应在对应分配得到证明后再设计，避免复用含有过期取消或订阅状态的对象。

## 10 回归与性能验收

### 10.1 行为回归

下列是各阶段的验证要求；实际通过范围与证据以分阶段交付记录为准。

| 场景 | 应验证的行为 |
|---|---|
| 单帧、空文本、多帧、UTF8 字符跨段 | 内容与原实现一致；单帧大小检查不能被绕过 |
| 刚好达到和超过 MaxMessageBytes | 上限保持一致；拒绝后仍可按原规则处理下一条合法消息 |
| 二进制消息、错误协议及错误 JSON | 拒绝、继续接收或关闭的行为与现有路径一致 |
| 取消、超时、Close、异常 | 无未完成 I/O 提前归还，无泄漏或重复归还 |
| 多连接并发、连接重建 | 消息不串线；旧连接归还不会破坏新连接接收 |
| 池返回更大且含旧内容的数组 | 只接收配置范围，只解析实际字节数，不读到尾部残留 |
| 完整与轻量事件、混合等级订阅 | 元数据和升级降级规则保持兼容 |
| Context 的大小写键、冲突键及 Unicode 键 | 比较器和失败语义保持一致 |
| 时间戳、未知字段、嵌套对象、数组、null 和大整数 | 转换前后值、精度和元数据语义一致 |
| 已发布事件被延迟处理或保留引用 | 后续消息不会覆盖此前事件内容 |

复用现有 [服务端分片拒绝回归](../../TestCode/WebSocketServerPhase7Tests.cs#L303)、[客户端事件回传回归](../../TestCode/WebSocketEventReturnPhase5Tests.cs)、[协议回归](../../TestCode/WebSocketProtocolPhase2Tests.cs) 和 [时间戳回归](../../TestCode/WebSocketTimestampTests.cs)。

新增所有权测试可使用可跟踪租借和归还的测试池及可控 WebSocket，验证任务实际完成前数组不会归还。重点覆盖取消与并发消息串扰，而不是只断言代码调用了 Rent。

### 10.2 分配验证

先用固定消息内容、固定消息数量验证 P1、P2，再用真实 APP 验证完整链路。

- P1：预热后，受控连续接收不再每条消息固定创建一个 64 KiB 数组；真实运行允许池未命中时分配。
- P2：普通单帧不创建接收拼接 MemoryStream；分片最终解码不创建 ToArray 结果；返回字符串保持独立。
- P3：普通 Context 路径去掉普通字典到目标字典的整表复制；保留元数据的兼容分支允许使用旧路径；对象和值的兼容回归全部通过。
- 同时记录分配字节、GC 次数和暂停、稳定内存及租借未归还数量。ArrayPool 缓存本身不等同于泄漏。

AllocationTick 的 AllocationAmount64 是采样间隔分配估计，不能直接当作该类型的精确字节占比。端到端分配总量优先使用各进程的运行时分配计数；异步接收跨线程，不能用跨 await 的 GetAllocatedBytesForCurrentThread 差值代表整个操作。

### 10.3 本机新旧对照

主配置保持 4 APP、1000 种事件、10 ms 发布间隔、8 B 载荷、往返模式、重订阅间隔 10 ms、fan-out 8、bucket 和 snapshot 各 60 秒、late window 60 秒。每个阶段记录组件哈希、编译配置、运行时和测量程序版本。

建议先进行同机 Release 版本至少三轮交替对照，每轮正式发布 5 分钟，并等待完整迟到窗口。诊断跟踪单独运行，覆盖前半段和后半段；记录可用内存、后台负载与每分钟实际发布速率，避免把采集扰动混入主要对照。

| 指标 | 比较方式 |
|---|---|
| 分配 | 四个 APP 分配字节总量除以实际 SentTick；可控接收测试另报每条消息字节数 |
| CPU | 各 APP 的 TotalProcessorTime 增量之和除以实际 SentTick，报告每次发布的 CPU ms |
| RTT | 按收到的唯一回包加权平均；每分钟 P99 单独报告，不伪称整轮全局 P99 |
| 完整性 | 同时报缺失、重复、乱序及期望量；退出码为 0 不能替代业务 PASS |
| 内存 | 预热后的均值、峰值和运行趋势；同时解释池缓存和活动缓冲占用 |

归一化指标使用相同的完整测量窗口，排除启动握手，并计入窗口对应的回包收尾。若缺失、重复异常仍存在，先解决测量或交付正确性，再据此宣称性能提升。

P1、P2 的通过条件是目标分配确实下降、行为回归通过且 CPU 与 RTT 无超出重复波动范围的持续退化。CPU 或延迟改善幅度以实际对照为准，不预先承诺百分比。固定 10 ms 发布间隔限制输入速率，这些结果也不等于最大吞吐能力提升。

### 10.4 服务器耐久验证

本机各阶段通过后，再复用服务器的四组 24 小时配置验证 500 和 1000 种事件、4 和 6 APP。同一轮对照保持运行时、容器资源、协议等级和测量程序一致，重新生成版本清单。重点检查数组归还、重连、长期内存趋势及队列丢弃计数。

## 11 分阶段交付与回退

Q0、P1、P2、P3 分别形成可独立回退的改动和结果记录。每阶段报告代码差异、组件哈希、行为回归及归一化性能数据。

出现消息内容串扰、元数据变化、异常分类变化、未归还缓冲持续增长或性能持续退化时，回退对应阶段并保留原始数据。首轮不依赖新增全局开关或新的外部包；保持原接口和默认配置，可以减少回退与发布范围。

建议首先交付 Q0 和统一基线，其后依次交付 P1 接收数组复用、P2 单帧直接解码和分片去复制，再根据新的采样结果推进 P3。这样能先验证证据最明确的分配减少，再决定是否值得承担发送缓冲、解析器或调度改造的复杂度。
