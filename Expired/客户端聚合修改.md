这份《客户端订阅聚合实现方案》写得**非常专业且严谨**！从数据结构设计、并发锁控制（`clientSubscriptionLock`）、生命周期管理（Dispose/重连）、到异常情况和详尽的 15 个测试用例，完全达到了企业级组件的 PR (Pull Request) 标准。

但是，在深度推演数据流之后，我发现方案中隐藏着一个**致命的逻辑漏洞（Fatal Flaw）**。这个漏洞会导致在某些常见场景下，你原本想要消灭的“重复触发”Bug 依然会原封不动地出现。

以下是详细的 Review 报告，分为**致命问题剖析**和**次要优化建议**。

---

### 🚨 致命问题：交集 Filter 导致的“重入爆炸”

在方案的 **17.2** 和 **17.3** 中，你明确了两个关键设计决策：
1. 客户端以**“完整的 Filter”**为聚合维度（只要有一点不同，就生成不同的 `MasterTokenId`）。
2. 收到远程事件后，**仍然扔进本地 EventHub 进行全局广播**。

**这两个决策结合在一起，会引发以下灾难场景：**

#### 场景推演（请看这个测试用例）：
假设客户端有三个 UI 组件：
*   **组件 A (Token_A)** 订阅：`[/thing/a Changed]`
*   **组件 B (Token_B)** 订阅：`[/thing/a Changed] AND [/thing/b Changed]`
*   **组件 C (Token_C)** 订阅：`[/thing/a Changed] AND [/thing/c Changed]`

**步骤 1：按照你的方案，客户端聚合结果为：**
*   Group 1 (`Master_1`): 包含 Token_A。发送网络请求 Sub(`Master_1`, `[a]`)
*   Group 2 (`Master_2`): 包含 Token_B。发送网络请求 Sub(`Master_2`, `[a, b]`)
*   Group 3 (`Master_3`): 包含 Token_C。发送网络请求 Sub(`Master_3`, `[a, c]`)

**步骤 2：服务端触发 `/thing/a Changed` 事件：**
*   服务端聚合层发现：`Master_1`, `Master_2`, `Master_3` 都匹配该事件。
*   服务端通过 WebSocket 向客户端下发 **3 条** `RemoteEventMessage`。

**步骤 3：客户端接收并处理（灾难发生）：**
*   客户端收到第 1 条消息（带 `Master_1`），校验存在，**扔进本地 EventHub**。
    *   本地 EventHub 广播，触发 Token_A, Token_B, Token_C 各一次。
*   客户端收到第 2 条消息（带 `Master_2`），校验存在，**又扔进本地 EventHub**。
    *   本地 EventHub 广播，再次触发 Token_A, Token_B, Token_C 各一次。
*   客户端收到第 3 条消息（带 `Master_3`），校验存在，**再扔进本地 EventHub**。
    *   本地 EventHub 广播，再次触发 Token_A, Token_B, Token_C 各一次。

**最终结果**：
服务端仅仅发生了一次 `/thing/a` 变更，但你的客户端 A、B、C 组件**每个人都收到了 3 次重复回调**。问题非但没解决，在复杂订阅下反而变得更隐蔽了！

### 🛠️ 核心破局方案（二选一）

既然 17.3 明确了**“无法做到 Token 精准路由，必须保留本地 EventHub 广播”**，那么我们必须打破 17.2 的“按完整 Filter 聚合”。

#### 方案一：客户端 Filter 拆散聚合（最符合当前架构，强烈推荐！）
既然本地的 EventHub 是按 `Source + EventType` 广播的，那么客户端的网络聚合也必须按**最小粒度**进行。

**修改点：**
不要再把整个 `EventFilter` 当作 GroupKey。
当一个 `Token` 传入 `Subscribe(token, filter)` 时，遍历 `filter.SourcesAndTypes`，将它**拆解为多个单一的订阅组**。

```csharp
// 伪代码思路
foreach(var item in filter.SourcesAndTypes)
{
    var groupKey = new ClientSubscriptionGroupKey(endpoint, item.Source, item.EventType);
    
    // 如果这个 (Source, EventType) 之前没订阅过，向服务器发起仅包含这一个 item 的 Subscribe
    // 如果已经订阅过，就把 local token 挂到这个组下，不发网络请求
}
```

**方案一的收益：**
回到上面的场景：A 要 `[a]`，B 要 `[a,b]`。
拆散后，客户端内存里只有两个 Group：`Group_A` (包含 TokenA, TokenB) 和 `Group_B` (包含 TokenB)。
客户端只向服务端发送两次 WS 请求：Sub(`Master_A`, `[a]`) 和 Sub(`Master_B`, `[b]`)。
当 `/thing/a` 发生时，服务端只命中 `Master_A`，下发 **1 条**消息。
客户端收到后扔进本地 EventHub，完美触发 TokenA 和 TokenB 各一次。**逻辑完美闭环！**

#### 方案二：基于 EventId 的本地去重缓冲（次优防守）
如果你坚决不想拆散 Filter，那么你必须在拦截器收到 `RemoteEventMessage` 扔进本地 EventHub 之前做去重。
要求每次服务端发出的事件必须带有一个全局唯一的 `EventId`。
```csharp
private readonly MemoryCache _recentEventIds = new MemoryCache(...);

private void HandleRemoteEvent(RemoteConnection connection, RemoteEventMessage message)
{
    // 如果 100 毫秒内已经把这个事件扔进过 EventHub，则丢弃后续的其他 MasterToken 带来的冗余拷贝
    if (!_recentEventIds.TryAdd(message.EventArg.EventId, true, TimeSpan.FromSeconds(2)))
    {
        return; 
    }
    RaiseRemoteEvent(connection, message.EventArg);
}
```
*缺点：依赖业务层有 EventId，且有一定的缓存内存开销。*

### 🔍 其他细节 Review 与优化建议

排除上面的核心逻辑漏洞，你的代码级设计非常优秀，只有几个微小的优化点：

#### 1. 关于锁内的网络调用 (第 6 节 & 第 7 节)
```csharp
lock (clientSubscriptionLock)
{
    UnsubscribeLocalBindingCore(token.Id, sendRemoteUnsubscribe: true);
}
```
你在 `UnsubscribeLocalBindingCore` 中使用了 `_ = ObserveBackgroundTask(SendUnsubscribe...)`，这是典型的 **Fire-and-Forget**。这是**极其正确**的做法。它避免了网络 IO 阻塞全局锁，也防止了死锁风险。请务必在代码注释中强调：*“此处必须为异步不等待，严禁同步调用或 await，以防死锁 clientSubscriptionLock”*。

#### 2. `ConcurrentDictionary<Guid, byte>` 的使用 (第 3.2 节)
在 `ClientSubscriptionGroup` 中，你用 `ConcurrentDictionary<Guid, byte>` 来当作并发的 `HashSet`。这是标准的 .NET 高性能做法（在 .NET 5+ 中甚至比单纯的锁+HashSet 更好）。给个赞！

#### 3. 内存泄漏防范：孤儿 Token 的清理
方案中提到 `Dispose()` 会清空 `clientSubscriptionGroups`。
但如果某个 UI 组件销毁时**忘记调用 UnSubScribe**，这个 `localTokenId` 将永远留在你的聚合组里，导致这个事件永远不会向服务端发送退订请求。
*建议*：如果可能，依赖注入系统或生命周期管理能提供一个机制：当判定某个 Connection 或作用域结束时，批量清理对应的 Local Tokens。如果不方便实现，暂且依靠最终的整体 `Dispose` 也可接受。

#### 4. FilterSignature 的拼接符风险 (第 5 节)
```csharp
$"{Escape(item.Source)}\u001F{Escape(item.EventType)}"
```
你使用了 ASCII 控制字符作为分隔符，这是一个非常聪明的防碰撞技巧。只要确保 `Escape` 方法足够健壮（考虑到 source 可能包含任意字符，甚至 JSON，或者本身就带有特殊控制符），这块没问题。

#### 5. 测试用例补充 (第 15 节)
必须补充一个测试用例，即我上面指出的盲点：
*   **15.16 交集 Filter 不导致本地广播风暴**
    *   场景：`token1` 订阅 `[A]`，`token2` 订阅 `[A, B]`。服务端只下发一次 `A` 事件。
    *   断言：本地回调一共只触发两次（Token1 一次，Token2 一次）。

### 总结

这份方案的架构骨架、状态机流转、锁的粒度设计**完全合格甚至优秀**。

但 **17.2（完整Filter聚合）+ 17.3（本地EventHub二次广播）** 的组合存在理论上的悖论，会引发交集订阅时的重入爆炸风暴。

**强烈建议：** 采用我上面给出的**“方案一：客户端 Filter 拆散聚合”**，放弃对整个 `EventFilter` 求 Hash/Signature。按最基础的 `Source+EventType` 维度在客户端构建字典映射。这样既不需要改动服务端协议，又能完美适配你想要保留本地 EventHub 广播语义的需求。
