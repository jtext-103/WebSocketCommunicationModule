# WSCM 当前订阅流程分析

本文基于当前代码分析 `WebSocketCommunicationModule` 的完整订阅处理链路。当前实现同时承担两类角色：

1. 作为客户端：本地 `EventHub` 发起远程订阅时，WSCM 连接远端 WebSocket 服务端、发送 `subscribe`，接收远端事件后回流给本地 `EventHub`。
2. 作为服务端：远端 WebSocket 客户端连接本模块时，WSCM 接收 `subscribe`，在本地 `EventHub` 建立订阅，并把本地事件推回远端。

当前代码位置：

- 客户端订阅入口：`WebSocketCommunicationModule/WebSocketCommunicationModule.cs`
- 客户端连接、发送、ACK、重连：`WebSocketCommunicationModule/WebSocketCommunicationModule.Client.cs`
- 远端事件回调：`WebSocketCommunicationModule/WebSocketCommunicationModule.Events.cs`
- 客户端连接状态模型：`WebSocketCommunicationModule/Connections/*`
- 服务端监听与会话：`WebSocketCommunicationModule/Server/WebSocketEventServer.cs`
- 服务端会话订阅：`WebSocketCommunicationModule/Server/WebSocketSession.cs`
- 协议消息：`WebSocketCommunicationModule/Protocol/*`

## 1. 关键数据结构

### 1.1 客户端侧连接表

`WebSocketCommunicationModule` 内部维护：

```csharp
private readonly ConcurrentDictionary<RemoteEndpointKey, RemoteConnection> connections = new();
private readonly ConcurrentDictionary<Guid, SubscriptionEntry> subscriptions = new();
```

含义：

- `connections`：按远端 endpoint 聚合连接。同一个远端 `RemoteEndpointKey` 只创建一个 `ClientWebSocket`。
- `subscriptions`：按本地 `Token.Id` 记录订阅状态。

`RemoteConnection` 内部还有：

```csharp
public ConcurrentDictionary<Guid, EventFilter> Filters { get; } = new();
public ClientWebSocket? WebSocket { get; set; }
public RemoteConnectionState State { get; set; }
public SemaphoreSlim SendLock { get; } = new(1, 1);
public SemaphoreSlim ConnectLock { get; } = new(1, 1);
```

含义：

- `Filters`：该远端连接下所有 token 对应的过滤器。
- `SendLock`：串行化同一个 WebSocket 上的发送。
- `ConnectLock`：防止同一个 endpoint 并发创建多个连接。

### 1.2 客户端侧订阅状态

`SubscriptionEntry` 保存：

- `TokenId`
- `Endpoint`
- `Filter`
- `State`
- `CreatedAtUtc`
- `ActivatedAtUtc`
- `SubscribeSentAtUtc`
- `LastError`

状态枚举 `SubscriptionState` 当前用于表达：

- `Pending`：已记录本地订阅，等待连接完成或等待发送/ACK。
- `Active`：收到远端 `subscribeAck.accepted = true`。
- `Failed`：连接失败、ACK 拒绝或收到错误消息。

当前实现中没有服务端 ACK 形式的取消订阅状态，`UnSubScribe` 是本地清理优先、网络通知尽力而为。

### 1.3 服务端侧会话订阅表

每个 `WebSocketSession` 内部维护：

```csharp
private readonly ConcurrentDictionary<Guid, ServerSubscriptionEntry> subscriptions = new();
```

这里的 key 是远端客户端传来的 `SubscribeMessage.TokenId`。`ServerSubscriptionEntry` 保存：

- `RemoteTokenId`：远端 token。
- `LocalToken`：调用本地 `eventHub.Subscribe(...)` 后返回的本地 token。
- `Filter`：清空 `Host` 后的本地过滤器。

注意：当前服务端订阅表是 session 级别的，不是全局聚合表。多个远端 session 订阅相同 `(source, eventType)` 时，会分别调用本地 `EventHub.Subscribe(...)`。

## 2. 客户端侧订阅主流程

入口是：

```csharp
public override void Subscribe(Token token, EventFilter filter)
```

处理顺序：

1. 校验 `token`、`filter`、`filter.Host`。
2. 克隆 `EventFilter`，避免外部后续修改影响内部状态。
3. 用 `RemoteEndpointKey.Parse(clonedFilter.Host)` 得到远端 endpoint。
4. 从 `connections` 获取或创建 `RemoteConnection`。
5. 把 `clonedFilter` 写入 `connection.Filters[token.Id]`。
6. 把 `SubscriptionEntry` 写入 `subscriptions[token.Id]`，初始状态为 `Pending`。
7. 取消该连接的 idle release timer。
8. 后台调用 `EnsureConnectedAsync(connection)`。

用流程图表示：

```text
EventHub.Subscribe
  -> WSCM.Subscribe(token, filter)
  -> Parse filter.Host as RemoteEndpointKey
  -> connections.GetOrAdd(endpoint)
  -> connection.Filters[token.Id] = clonedFilter
  -> subscriptions[token.Id] = Pending
  -> EnsureConnectedAsync(connection)
```

这个入口本身不等待网络完成。订阅是否真正成功由后台连接、发送 `subscribe`、收到 `subscribeAck` 后决定。

## 3. 客户端连接与握手

`EnsureConnectedAsync(connection)` 是连接编排入口。

处理逻辑：

1. 如果模块已释放或连接已释放，直接返回。
2. 获取 `connection.ConnectLock`，保证同一个 endpoint 只有一个连接流程。
3. 如果 WebSocket 已打开且状态为 `Connected`，调用 `FlushSubscriptionsAsync(connection)`，只补发还没发过的 pending 订阅。
4. 否则把状态置为 `Connecting`，进入 `ConnectAndHandshakeAsync(connection)`。

`ConnectAndHandshakeAsync` 做的事情：

1. Dispose 旧的 `ClientWebSocket`。
2. 创建新的 `ClientWebSocket`。
3. 添加 subprotocol：`cfet2-event.v2`。
4. 如果配置了认证，则设置 `Authorization` header。
5. 在 `ConnectTimeout` 内连接远端 `/cfet2/event/v2`。
6. 校验远端接受的 subprotocol。
7. 发送 `HelloMessage`。
8. 在 `HandshakeTimeout` 内等待 `HelloAckMessage`。
9. 如果 `helloAck.Accepted == false`，连接失败。
10. 设置 `LastReceivedAtUtc`、`RetryCount = 0`、`State = Connected`。
11. 启动 `ReceiveLoopAsync` 和 `HeartbeatLoopAsync`。
12. 通过 `RaiseConnectionStatus(... Connected ...)` 上报连接成功。
13. 调用 `FlushSubscriptionsAsync(connection)` 发送订阅。

## 4. 客户端发送 subscribe 的 Flush 流程

`FlushSubscriptionsAsync(connection)` 负责把该连接下尚未发送的 pending 订阅发给远端。

核心筛选条件：

```csharp
entry.Endpoint == connection.Endpoint
entry.State == SubscriptionState.Pending
entry.SubscribeSentAtUtc == null
```

符合条件才发送：

```csharp
new SubscribeMessage
{
    TokenId = entry.TokenId,
    Filter = entry.Filter,
}
```

发送成功后：

- 设置 `entry.SubscribeSentAtUtc = DateTime.UtcNow`。
- 如果 `options.ResubscribeInterval > TimeSpan.Zero`，相邻订阅之间延迟一段时间。

发送失败后：

- 记录 `entry.LastError`。
- 把 `SubscribeSentAtUtc` 置回 `null`。
- 调用 `MarkConnectionFailed(connection, ex.Message)`。

重要行为：

- 同一连接上的订阅是逐条发送，不是批量消息。
- 当前实现通过 `SubscribeSentAtUtc` 防止同一个 pending 订阅在连接正常时重复发送。
- 重连时会清空 `SubscribeSentAtUtc`，使 Active/Pending 订阅重新发送。

## 5. 客户端处理 subscribeAck

客户端接收循环在 `ReceiveLoopAsync(connection)` 中运行。

收到完整 text message 后：

1. 反序列化成 `WebSocketMessageEnvelope`。
2. 调用 `HandleIncomingMessage(connection, message)`。
3. 如果是 `SubscribeAckMessage`，进入 `HandleSubscribeAck`。

`HandleSubscribeAck` 逻辑：

- 如果找不到 `subscriptions[message.TokenId]`，忽略。
- 如果 `message.Accepted == true`：
  - `entry.State = Active`
  - `entry.ActivatedAtUtc = DateTime.UtcNow`
  - `entry.LastError = null`
- 如果 `message.Accepted == false`：
  - `entry.State = Failed`
  - `entry.LastError = message.Reason ?? "Subscribe rejected."`

注意：ACK 拒绝后，当前代码没有自动从 `subscriptions` 或 `connection.Filters` 中移除该 token，只是把状态标为 `Failed`。

## 6. 客户端接收远端事件并回流 EventHub

远端推送业务事件使用 `RemoteEventMessage`：

```csharp
public sealed class RemoteEventMessage : WebSocketMessageEnvelope
{
    public Guid? TokenId { get; init; }
    public EventArg? EventArg { get; init; }
}
```

客户端当前处理逻辑：

1. `HandleIncomingMessage` 匹配到 `RemoteEventMessage`。
2. `HandleRemoteEvent` 检查 `message.EventArg != null`。
3. 调用 `RaiseRemoteEvent(connection, message.EventArg)`。
4. `RaiseRemoteEvent` 把 `eventArg.Host` 设置为 `connection.Endpoint.NormalizedHost`。
5. 如果 `eventArg.Sample != null`，设置 `eventArg.Sample.IsRemote = true`。
6. 调用 `InvokeEventCallback(eventArg)`。

`eventCallback` 是 `RegisterEventCallback` 保存的 Core 回调，通常指向本地 `EventHub.ReceiveRemoteEvent(...)`。因此 WSCM 不直接调用业务 handler，而是把事件回流给 EventHub，由 EventHub 再按本地 remote subscriber 分发。

当前客户端不依赖 `RemoteEventMessage.TokenId` 做本地分发，该字段只是可选信息；无 token 时按广播式远程事件处理。

## 7. 客户端取消订阅流程

入口是：

```csharp
public override void UnSubScribe(Token token)
```

处理顺序：

1. `token == null` 时直接返回。
2. 从 `subscriptions` 移除 `token.Id`。
3. 如果订阅不存在，直接返回，保证幂等。
4. 找到对应 `connection`。
5. 从 `connection.Filters` 移除 `token.Id`。
6. 判断该连接是否已经没有任何订阅。
7. 后台调用 `SendUnsubscribeAndScheduleReleaseIfIdleAsync(...)`。

`SendUnsubscribeAndScheduleReleaseIfIdleAsync` 中：

1. 如果连接还打开且状态是 `Connected`，发送：

```csharp
new UnsubscribeMessage { TokenId = tokenId }
```

2. 发送失败只记录 warning，不回滚本地清理。
3. 如果这是该连接最后一个订阅，执行 idle release 策略。

取消订阅原则：

- 本地状态先清理。
- 网络 `unsubscribe` 是 fire-and-forget。
- 重复取消同一个 token 不会重复发送 unsubscribe。
- 取消一个 token 不影响同一连接下的其他 token。

## 8. 空闲连接释放

当某个连接下最后一个订阅被取消后，调用 `ScheduleIdleRelease(connection)`。

释放策略由配置决定：

- `ReleaseConnectionImmediatelyWhenIdle == true`：立即释放。
- `IdleReleaseDelay <= TimeSpan.Zero`：立即释放。
- 否则创建 timer，延迟到期后释放。

真正释放在 `ReleaseConnectionIfIdle(connection)`：

1. 再次检查 `connection.Filters.IsEmpty`。
2. 从 `connections` 移除该 endpoint。
3. Dispose `RemoteConnection`，从而取消 CTS、释放 timer、WebSocket 和锁。

如果 idle delay 期间又有新订阅加入，`Subscribe` 会 Dispose 掉 `connection.IdleReleaseTimer`，避免连接被错误释放。

## 9. 客户端断线、心跳和重连补订

### 9.1 Receive loop 触发重连

`ReceiveLoopAsync` 读取 WebSocket 消息。如果读取或解析连接层消息失败，会：

1. 设置 `connection.State = Disconnected`。
2. 上报 `ConnectionStatusEvent.Disconnected`。
3. 调用 `ScheduleReconnectIfNeeded(connection, ex.Message)`。

只有连接仍有订阅时才会进入重连：

```csharp
if (disposed ||
    connection.State == RemoteConnectionState.Disposed ||
    connection.Filters.IsEmpty)
{
    return;
}
```

### 9.2 心跳触发重连

`HeartbeatLoopAsync` 定期发送 `PingMessage`。如果：

```csharp
DateTime.UtcNow - connection.LastReceivedAtUtc > options.HeartbeatTimeout
```

则：

1. Abort 当前 WebSocket。
2. 状态置为 `Disconnected`。
3. 上报断线。
4. 进入重连。

收到任意消息时 receive loop 会刷新 `LastReceivedAtUtc`；收到 `PongMessage` 也会刷新。

### 9.3 重连补订

`ReconnectLoopAsync` 循环执行：

1. `connection.RetryCount++`。
2. `connection.State = Reconnecting`。
3. 调用 `ResetSubscriptionsForReconnect(connection)`。
4. 上报 `ConnectionStatusEvent.Reconnecting`。
5. 等待 `GetReconnectDelay(connection.RetryCount)`。
6. 调用 `EnsureConnectedAsync(connection)`。

`ResetSubscriptionsForReconnect` 会把该连接下仍存在的 `Active` 或 `Pending` 订阅重置为：

- `State = Pending`
- `ActivatedAtUtc = null`
- `SubscribeSentAtUtc = null`

所以重连成功后，`FlushSubscriptionsAsync` 会重新发送这些订阅。

如果重连期间最后一个订阅被取消，`connection.Filters.IsEmpty` 会让重连循环停止，随后连接可被释放。

## 10. 服务端接收订阅流程

服务端由 `WebSocketEventServer` 启动。

`Start()` 中：

1. 校验 `options.ListenUri`。
2. 创建 Kestrel app。
3. `UseWebSockets()`。
4. 只映射 `WebSocketProtocolConstants.EndpointPath`，即 `/cfet2/event/v2`。

收到请求时 `HandleContextAsync`：

1. 如果不是 WebSocket 请求，返回 `400 BadRequest`。
2. 检查请求 subprotocol 是否包含 `cfet2-event.v2`。
3. 接受 WebSocket。
4. 创建 `WebSocketSession`。
5. 调用 `session.RunAsync(cts.Token)`。
6. session 结束后从 `sessions` 移除并 Dispose。

## 11. 服务端 session 内订阅流程

`WebSocketSession.RunAsync` 中：

1. 先执行 `HandshakeAsync`。
2. 循环接收消息。
3. 按消息类型分发：
   - `SubscribeMessage` -> `SubscribeAsync`
   - `UnsubscribeMessage` -> `UnsubscribeAsync`
   - `PingMessage` -> 回复 `PongMessage`
   - 其他消息 -> 回复 `ErrorMessage`

### 11.1 服务端握手

`HandshakeAsync` 要求第一条消息必须是 `HelloMessage`。

- 如果不是 hello，发送 `ErrorMessage { Code = "handshakeExpected" }` 并抛异常结束 session。
- 如果是 hello，发送 `HelloAckMessage { Accepted = true }`。

当前服务端没有实际鉴权逻辑，`HelloAck` 默认接受。

### 11.2 服务端 SubscribeAsync

收到 `SubscribeMessage` 后：

1. 如果 `message.Filter == null`，回复 `SubscribeAckMessage { Accepted = false, Reason = "Filter is required." }`。
2. 先对同一个 `message.TokenId` 调用 `UnsubscribeLocal(message.TokenId)`，避免重复 token 残留旧订阅。
3. 克隆远端 filter，并设置 `Host = string.Empty`，转换为本地 EventHub filter。
4. 调用：

```csharp
eventHub.Subscribe(localFilter, eventArg => _ = SendLocalEventAsync(eventArg));
```

5. 保存到 session 内 `subscriptions[message.TokenId]`。
6. 回复 `SubscribeAckMessage { TokenId = message.TokenId, Accepted = true }`。

关键点：

- 远端 filter 中的 `Host` 不会用于本地 EventHub 匹配。
- 本地订阅 token 只保存在当前 session 里。
- 同一个 session 内同一个远端 token 再次订阅，会先取消旧的本地订阅。

### 11.3 服务端事件推送

本地 `EventHub` 触发匹配事件后，调用订阅时传入的回调：

```csharp
eventArg => _ = SendLocalEventAsync(eventArg)
```

`SendLocalEventAsync` 会发送：

```csharp
new RemoteEventMessage
{
    EventArg = eventArg,
}
```

当前服务端推送可以不设置 `TokenId`。远端客户端需要根据收到的 `EventArg` 自行回流到自己的 EventHub 进行二次匹配。

### 11.4 服务端取消订阅

收到 `UnsubscribeMessage` 后：

1. 调用 `UnsubscribeLocal(remoteTokenId)`。
2. 不发送 ACK。

`UnsubscribeLocal`：

1. 从 session 的 `subscriptions` 移除远端 token。
2. 如果存在本地 `LocalToken`，调用 `eventHub.Unsubscribe(entry.LocalToken)`。
3. 异常会被吞掉，不影响 session。

### 11.5 服务端 session 关闭清理

`WebSocketSession.Dispose()` 中：

1. 标记 disposed。
2. 取消 `cts`。
3. 遍历 `subscriptions.Keys`。
4. 对每个远端 token 调用 `UnsubscribeLocal`。
5. Dispose socket、sendLock、cts。

因此远端连接断开时，该 session 下创建的本地 EventHub 订阅会被清理。

## 12. 当前订阅链路时序图

### 12.1 客户端订阅远端

```text
Local EventHub
  -> WSCM.Subscribe(token, filter)
  -> Save Pending subscription
  -> EnsureConnectedAsync
  -> ClientWebSocket.ConnectAsync
  -> send hello
  <- recv helloAck
  -> FlushSubscriptionsAsync
  -> send subscribe(tokenId, filter)
  <- recv subscribeAck(accepted)
  -> mark subscription Active
  <- recv event(EventArg)
  -> set EventArg.Host = endpoint host
  -> set Sample.IsRemote = true
  -> eventCallback(EventArg)
  -> Local EventHub.ReceiveRemoteEvent
```

### 12.2 远端订阅本模块

```text
Remote Client
  -> WebSocket upgrade /cfet2/event/v2 with cfet2-event.v2
  -> send hello
  <- recv helloAck
  -> send subscribe(tokenId, filter)

WSCM WebSocketSession
  -> clone filter and clear Host
  -> local EventHub.Subscribe(localFilter, SendLocalEventAsync)
  -> save ServerSubscriptionEntry in session
  <- send subscribeAck(accepted)

Local EventHub.Publish
  -> matching local subscription callback
  -> SendLocalEventAsync
  <- remoteEvent(EventArg)
```

## 13. 已由测试覆盖的主要行为

当前测试覆盖了以下订阅相关行为：

- `subscribeAck.accepted = true` 后订阅进入 `Active`。
- `subscribeAck.accepted = false` 后订阅进入 `Failed` 并记录原因。
- 同一 endpoint 多个 token 复用一个 WebSocket 连接。
- 已连接后新增订阅，只 flush 新 token。
- `UnSubScribe` 先移除本地状态，再发送 `unsubscribe`。
- 取消一个 token 不影响同连接其他 token。
- 重复取消订阅是幂等的。
- 心跳超时或服务端关闭后会重连并重新订阅。
- 重连期间取消最后一个 token 会停止重连并释放连接。
- idle release 和 immediate release 都能释放空闲连接。
- 服务端能接受 hello 和 subscribe。
- 服务端能把本地事件推给远端订阅者。
- 服务端订阅时会把远端 filter 转为本地 filter，即清空 `Host`。
- 服务端收到 unsubscribe 后停止推送该 token。
- session 关闭会清理本地订阅。
- 服务端能处理多个并发 subscriber。

## 14. 当前实现的限制和风险点

### 14.1 服务端没有全局订阅聚合

当前 `WebSocketSession` 每个 session 自己维护订阅：

```csharp
private readonly ConcurrentDictionary<Guid, ServerSubscriptionEntry> subscriptions = new();
```

这意味着：

- 100 个远端客户端订阅同一个 `source/eventType`，服务端会调用 100 次本地 `EventHub.Subscribe(...)`。
- 本地事件触发时，EventHub 会分别触发 100 个回调。
- 这能工作，但不具备跨 session 去重和精确聚合能力。

仓库根目录的 `修复多重订阅问题.md` 提到的全局 `WebSocketSubscriptionManager` 尚未落到当前代码里。

### 14.2 服务端推送未携带 tokenId

`RemoteEventMessage` 支持可选 `TokenId`，但当前 `SendLocalEventAsync` 可以只发送 `EventArg`。

这符合“客户端由 EventHub 二次分发”的模型，但远端无法直接知道是哪一个远端 token 命中。若未来要做远端侧性能优化或精确确认，需要补充单个 token 信息。

### 14.3 ACK 拒绝后不自动清理订阅表

客户端收到 `subscribeAck.accepted = false` 后只把 entry 标为 `Failed`。`connection.Filters` 中对应 token 仍可能存在。

影响：

- 后续重连时 `ResetSubscriptionsForReconnect` 只重置 `Active` 或 `Pending`，不会重置 `Failed`。
- 该 token 仍占在 `connection.Filters` 中，可能影响连接是否被判断为空闲。

是否需要清理取决于产品语义：如果 Failed 订阅允许用户查看失败状态并稍后重试，可以保留；如果失败即终止，应同时移除 `connection.Filters` 并考虑释放连接。

### 14.4 服务端没有 session 级心跳超时剔除

服务端当前能响应客户端 `PingMessage`，但没有独立的 heartbeat loop 去检测长时间无消息的 session。异常断开通常依赖 socket receive 抛异常后清理。

### 14.5 `RemoteEventMessage.TokenId` 未参与客户端分发

客户端不按 `TokenId` 直接投递，统一交给 `EventHub` 匹配。这是当前设计选择，不是 bug。但如果远端推送了一个与本地 filter 不匹配的事件，客户端不会按 token 强制投递。

### 14.6 Subscribe 日志访问第一个 filter 项有越界风险

`Subscribe` 末尾日志直接访问：

```csharp
filter.SourcesAndTypes[0]
```

如果 `SourcesAndTypes.Count == 0`，会抛异常。当前入口只校验了 `filter.Host`，没有校验 `SourcesAndTypes` 非空。

## 15. 小结

当前 WSCM 订阅流程可以概括为：

- 客户端侧：按 endpoint 复用 WebSocket，按 token 维护订阅状态，通过 `Pending -> Active/Failed` 管理生命周期；断线后对仍存在的 Active/Pending 订阅进行重连补订；取消订阅本地清理优先。
- 服务端侧：按 WebSocket session 维护远端 token 到本地 EventHub token 的映射；收到远端订阅就创建本地订阅；本地事件触发后通过 WebSocket 推送 `RemoteEventMessage`；unsubscribe 或 session 关闭时清理本地订阅。
- 当前没有实现跨 session 的服务端全局订阅聚合，因此“大量远端相同订阅”会映射成大量本地 EventHub 订阅。若要解决多重订阅风暴，需要引入全局聚合订阅管理器。
