# 客户端订阅聚合管理器拆分方案

本文说明如何从 `WebSocketCommunicationModule` 中抽出客户端订阅聚合管理器，以减轻模块门面类的职责。本文只描述拆分方案，不直接改变当前运行行为。

## 1. 当前问题

当前 `WebSocketCommunicationModule` 同时承担三类职责：

1. 对外实现 `IEventCommunicationModule`，作为 Core 与 WebSocket 模块之间的门面。
2. 管理服务端生命周期和远端 endpoint client 池。
3. 管理客户端侧订阅聚合：
   - 将一个本地 `EventFilter` 拆成多个 `(endpoint, source, eventType)` 聚合 key。
   - 为每个聚合 key 创建远端 master token。
   - 维护本地 token 到多个 master token 的映射。
   - 维护多个本地 token 对同一个远端订阅的引用计数。
   - 判断什么时候需要发送真实 `subscribe` 或 `unsubscribe`。

第 1、2 类属于模块门面职责；第 3 类已经是独立的客户端订阅聚合算法，继续放在门面类中会让 `WebSocketCommunicationModule` 过重。

## 2. 拆分目标

拆分后建议形成如下职责边界：

| 类 | 拆分后职责 |
| --- | --- |
| `WebSocketCommunicationModule` | 对接 Core、生命周期管理、保存 event callback、创建/释放 `RemoteEndpointClient`、转发远端事件和连接状态 |
| `ClientSubscriptionAggregator` | 管理客户端侧本地订阅到远端聚合订阅的映射，并输出需要对远端 client 执行的动作 |
| `RemoteEndpointClient` | 单 endpoint 连接状态机，负责连接、握手、发送 subscribe/unsubscribe、接收事件、心跳、重连和 idle release |

拆分原则：

- 聚合管理器不直接操作 socket。
- 聚合管理器不直接启动连接。
- 聚合管理器不直接回调 Core。
- 聚合管理器只维护内存状态，并返回“需要执行的远端动作”。
- `WebSocketCommunicationModule` 仍负责把这些动作应用到 `RemoteEndpointClient`。

## 3. 建议新增类

### 3.1 `ClientSubscriptionAggregator`

建议位置：

```text
WebSocketCommunicationModule/Client/ClientSubscriptionAggregator.cs
```

建议可见性：

```csharp
internal sealed class ClientSubscriptionAggregator
```

核心职责：

- 保存所有客户端侧订阅聚合状态。
- 处理本地 token 的 subscribe / unsubscribe。
- 生成远端单规则 `EventFilter`。
- 维护本地 token 与 master token 的绑定。
- 判断哪些远端聚合订阅是新增的。
- 判断哪些远端聚合订阅没有本地引用，需要远端取消。
- 在连接空闲释放后清理状态时保持一致性。

不应该承担的职责：

- 不创建 `RemoteEndpointClient`。
- 不调用 `EnsureConnectedAsync`。
- 不调用 `SendUnsubscribeAsync`。
- 不处理 `RemoteEventMessage`。
- 不处理连接状态事件。
- 不记录网络连接日志。

## 5. 建议结果对象

聚合管理器处理订阅后，需要告诉门面类投递哪些 endpoint 动作。评审修订后，实施版使用一个统一的 `ClientSubscriptionPlan`，同时承载 subscribe 和 unsubscribe actions。一次“更新订阅”可能同时产生新增远端订阅和取消旧远端订阅，因此不再拆成两个 plan 类型。

## 6. 建议公开方法

`ClientSubscriptionAggregator` 建议提供以下方法：

```csharp
internal sealed class ClientSubscriptionAggregator
{
    public ClientSubscriptionPlan Subscribe(Token token, EventFilter filter);

    public ClientSubscriptionPlan Unsubscribe(Token token);

    public bool HasLocalSubscriptions(RemoteEndpointKey endpoint);

    public void Clear();
}
```

### 6.1 `Subscribe`

输入：

- Core 传入的 `Token`。
- Core 传入的 `EventFilter`。

处理：

1. 校验 `token`、`filter`、`filter.Host`。
2. clone `EventFilter`，避免外部后续修改影响内部状态。
3. 用 `RemoteEndpointKey.Parse(clonedFilter.Host)` 得到 endpoint。
4. 基于 `SourcesAndTypes` 生成去重后的 `ClientSubscriptionGroupKey`。
5. 如果本地 token 已存在且 group 集合完全相同，返回空 plan。
6. 如果本地 token 已存在但 group 发生变化，先从旧 group 移除不再需要的引用。
7. 对每个新 group：
   - 已存在则只加入本地 token 引用。
   - 不存在则创建新的 `ClientSubscriptionGroup` 和 master token，并生成 `ClientRemoteSubscribeAction`。
8. 更新 `localSubscriptionIndex`。
9. 返回 subscribe plan。

输出：

- 新增远端聚合订阅动作。
- 由于订阅更新导致旧 group 失去最后引用，需要远端取消的动作。

### 6.2 `Unsubscribe`

输入：

- Core 传入的 `Token`。

处理：

1. token 为 null 时返回空 plan。
2. 从 `localSubscriptionIndex` 移除本地 token。
3. 如果 token 不存在，返回空 plan。
4. 从该 token 关联的所有 group 中移除本地引用。
5. 如果某个 group 已经没有本地 token 引用：
   - 从 `clientSubscriptionGroups` 移除。
   - 生成对应 `ClientRemoteUnsubscribeAction`。
6. 返回 unsubscribe plan。

### 6.3 `HasLocalSubscriptions`

用途：

- 判断某个 endpoint 是否仍然有本地订阅引用。
- 可用于 `WebSocketCommunicationModule` 判断 idle client 释放是否仍然安全。

当前 `RemoteEndpointClient.IsIdle` 已基于远端订阅数判断，这个方法不是必须，但可以让模块门面在极端并发场景下多一层状态校验。

### 6.4 `Clear`

用途：

- `WebSocketCommunicationModule.Dispose()` 时清理聚合状态。

## 7. 拆分后的 `WebSocketCommunicationModule.Subscribe`

拆分后，门面类中的 `Subscribe` 应变成“生成 plan + 投递 endpoint 顺序动作”的薄编排。注意：门面类不再直接调用 `AddOrUpdateSubscription`、`RemoveSubscription`、`SendUnsubscribeAsync`，否则会重新引入 plan 执行乱序风险。

```csharp
public override void Subscribe(Token token, EventFilter filter)
{
    ThrowIfDisposed();

    if (filter?.PerformanceLevel != 0)
    {
        logger.Warn("WebSocketCM does not support PerformanceLevel; full EventArg payload will be used.");
    }

    var plan = subscriptionAggregator.Subscribe(token, filter);
    EnqueueClientPlan(plan);
}
```

`EnqueueClientPlan` 只负责按 endpoint 找到 client，并把动作投递给该 endpoint 的顺序队列：

```csharp
private void EnqueueClientPlan(ClientSubscriptionPlan plan)
{
    foreach (var action in plan.SubscribeActions)
    {
        var client = endpointClients.GetOrAdd(action.Endpoint, CreateRemoteEndpointClient);
        client.EnqueueSubscribe(action.MasterTokenId, action.RemoteFilter);
    }

    foreach (var action in plan.UnsubscribeActions)
    {
        if (endpointClients.TryGetValue(action.Endpoint, out var client))
        {
            client.EnqueueUnsubscribe(action.MasterTokenId);
        }
    }
}
```

这个设计的关键点：

- aggregator 只提交本地聚合状态并生成动作。
- `WebSocketCommunicationModule` 只负责将动作送到正确的 endpoint client。
- 同一个 endpoint 上动作的真实应用顺序由 `RemoteEndpointClient` 内部队列保证。
- 已连接状态下新增订阅由 endpoint action loop 触发 `EnsureConnectedAsync` 或 `FlushSubscriptionsAsync`，不能依赖调用线程直接发送。

## 8. 拆分后的 `WebSocketCommunicationModule.UnSubScribe`

拆分后，门面类中的 `UnSubScribe` 同样只生成 plan 并投递动作：

```csharp
public override void UnSubScribe(Token token)
{
    if (token == null)
    {
        return;
    }

    var plan = subscriptionAggregator.Unsubscribe(token);
    EnqueueClientPlan(plan);
}
```

这样 `WebSocketCommunicationModule` 不再需要知道 group 引用计数、group key 去重和 master token 映射细节，也不会在多个调用线程中直接交错执行远端 subscribe/unsubscribe。

### 8.1 `RemoteEndpointClient` 顺序动作队列

为解决多线程 subscribe/unsubscribe 导致的动作乱序，`RemoteEndpointClient` 需要增加 endpoint 内部顺序动作队列。

建议新增内部动作类型：

```csharp
internal enum RemoteEndpointActionKind
{
    Subscribe,
    Unsubscribe
}

internal readonly record struct RemoteEndpointAction(
    RemoteEndpointActionKind Kind,
    Guid MasterTokenId,
    EventFilter? RemoteFilter);
```

建议新增方法：

```csharp
public void EnqueueSubscribe(Guid masterTokenId, EventFilter remoteFilter);

public void EnqueueUnsubscribe(Guid masterTokenId);
```

动作循环负责串行应用动作：

```csharp
private async Task ProcessActionsAsync()
{
    await foreach (var action in actionQueue.Reader.ReadAllAsync(lifetimeCts.Token))
    {
        switch (action.Kind)
        {
            case RemoteEndpointActionKind.Subscribe:
                AddOrUpdateSubscription(action.MasterTokenId, action.RemoteFilter!);
                await EnsureConnectedAsync().ConfigureAwait(false);
                break;

            case RemoteEndpointActionKind.Unsubscribe:
                if (RemoveSubscription(action.MasterTokenId))
                {
                    await SendUnsubscribeAsync(action.MasterTokenId).ConfigureAwait(false);
                }
                break;
        }
    }
}
```

实现约束：

- `EnqueueSubscribe` / `EnqueueUnsubscribe` 只能做入队，不做网络 IO。
- action loop 是同一 endpoint 的唯一订阅动作应用者。
- `EnsureConnectedAsync` 在已连接时必须 flush pending subscriptions。
- `SendUnsubscribeAsync` 仍保持尽力发送，失败不回滚本地状态。
- `Dispose` 时停止 action loop，并清理未执行动作。

如果第一版不想引入 `Channel`，可以用 endpoint 级锁保护“纯内存状态应用 + 异步任务投递顺序”。但这个方案只能作为过渡，长期推荐 action queue。

## 10. 并发与锁边界

拆分后建议锁边界集中在 `ClientSubscriptionAggregator` 内部：

```csharp
private readonly object syncRoot = new();
```

所有读写以下结构的逻辑都在该锁内完成：

- `clientSubscriptionGroups`
- `localSubscriptionIndex`

不要在持有 aggregator 锁时执行网络动作，也不要在调用线程里直接执行 endpoint 订阅动作：

- 不调用 `RemoteEndpointClient.AddOrUpdateSubscription`。
- 不调用 `EnsureConnectedAsync`。
- 不调用 `SendUnsubscribeAsync`。
- 不调用 `RemoveSubscription`。

原因：

- 聚合状态变更应快速完成。
- 网络动作可能触发异步等待、事件回调或锁竞争。
- 返回 plan 后再应用动作，可以避免聚合锁和连接锁交叉导致复杂死锁风险。
- plan 必须投递到 endpoint 顺序动作队列，保证同一 endpoint 上 subscribe/unsubscribe 按生成顺序应用。

同步阶段的异常约束：

- aggregator 内完成 token、filter、host、source/eventType、endpoint 解析校验。
- `CreateRemoteEndpointClient` 必须是纯内存构造，不做 DNS、连接或握手。
- `EnqueueSubscribe` / `EnqueueUnsubscribe` 必须尽量不抛异常；如果 action queue 已关闭，只记录日志并忽略。
- 所有 IO 异常只发生在 endpoint action loop、`EnsureConnectedAsync`、发送和接收循环中。

## 11. 行为保持要求

拆分后必须保持以下行为不变：

1. 同一 endpoint 下相同 `(source, eventType)` 只创建一个远端 master token。
2. 多个本地 token 订阅同一 `(endpoint, source, eventType)` 时，只发送一次真实 `subscribe`。
3. 最后一个本地 token 取消后，才发送真实 `unsubscribe`。
4. 同一 token 重复订阅完全相同 group 集合时，不重复发送网络动作。
5. 同一 token 更新订阅时，只取消不再需要的旧 group，只新增缺失的新 group。
6. `PerformanceLevel != 0` 仍保持当前不支持语义，远端 filter 使用 `PerformanceLevel = 0`。
7. `Subscribe` 和 `UnSubScribe` 仍是同步入口，不等待网络动作完成。
8. 网络发送失败不回滚本地聚合状态。
9. `Dispose` 时清空聚合状态，不再回调业务。
10. 同一 endpoint 上 plan 动作必须按生成顺序应用，不能出现 unsubscribe 先于对应 subscribe 的乱序执行。
11. 已连接状态下新增订阅必须触发 flush，不能因为 `EnsureConnectedAsync` 直接返回而丢失 subscribe。
12. aggregator 中被移除的最后一个 group 必须彻底从索引删除，不留下空 group 或空 endpoint 壳。
13. `LocalSubscriptionBinding` 必须保存完整 `GroupKeys`，作为后续更新订阅 diff 的依据。

## 12. 测试建议

拆分后建议新增或调整单元测试，重点验证 aggregator 自身行为：

1. 单 token 单 source/type 会生成一个 subscribe action。
2. 单 token 多 source/type 会生成多个 subscribe action。
3. 重复 source/type 会去重。
4. 多个 token 订阅相同 source/type 时，第二次不生成 subscribe action。
5. 取消其中一个 token 时，不生成 unsubscribe action。
6. 取消最后一个 token 时，生成 unsubscribe action。
7. 同一 token 重复订阅相同 group 集合时，不生成任何动作。
8. 同一 token 更新订阅时，正确生成新增 subscribe action 和旧 group unsubscribe action。
9. 只有创建新 master token 时才创建 remote filter，重复订阅已有 group 不做不必要 clone。
10. 空 `Host`、空 `SourcesAndTypes`、缺失 source/type 的处理与当前行为一致。
11. Subscribe 后立刻 UnSubScribe，同一 endpoint action loop 中必须按 subscribe -> unsubscribe 顺序应用。
12. UnSubScribe 后立刻 Subscribe，同一 endpoint action loop 中必须按 unsubscribe -> subscribe 顺序应用。

对 `WebSocketCommunicationModule` 的集成测试重点改为验证：

- 它能正确把 plan 投递到 `RemoteEndpointClient`。
- 它不再直接关心 group 引用计数。
- 远端事件和连接状态回调不受拆分影响。
- 它不直接调用 `AddOrUpdateSubscription` / `RemoveSubscription` / `SendUnsubscribeAsync`。

对 `RemoteEndpointClient` 的新增测试重点为：

- 多线程入队 subscribe/unsubscribe 时，动作应用顺序与入队顺序一致。
- 已连接时入队 subscribe 会触发 pending subscription flush。
- 入队 unsubscribe 会先移除本地 subscription，再尽力发送远端 unsubscribe。
- action loop 发生发送异常时不会退出整个 endpoint client。

## 13. 建议迁移步骤

### 步骤 1：新增结果 DTO 和 aggregator

新增：

```text
WebSocketCommunicationModule/Client/ClientSubscriptionAggregator.cs
WebSocketCommunicationModule/Client/ClientSubscriptionPlan.cs
WebSocketCommunicationModule/Client/ClientRemoteSubscribeAction.cs
WebSocketCommunicationModule/Client/ClientRemoteUnsubscribeAction.cs
```

先把当前聚合逻辑完整搬入 aggregator，并让测试覆盖内部行为。此步骤只处理内存状态和 plan 生成，不接触 `RemoteEndpointClient`。

### 步骤 2：给 `RemoteEndpointClient` 增加 endpoint 顺序动作队列

新增：

```text
RemoteEndpointActionKind
RemoteEndpointAction
EnqueueSubscribe(...)
EnqueueUnsubscribe(...)
ProcessActionsAsync(...)
```

迁移要求：

- `AddOrUpdateSubscription`、`RemoveSubscription`、`EnsureConnectedAsync`、`SendUnsubscribeAsync` 的调用统一进入 action loop。
- action loop 按入队顺序处理同一 endpoint 上的动作。
- `EnsureConnectedAsync` 保持当前语义：已连接时仍调用 `FlushSubscriptionsAsync`。
- `Dispose` 时取消 action loop，并释放队列。

### 步骤 3：替换 `WebSocketCommunicationModule.Subscribe`

让 `Subscribe` 调用 aggregator，按 plan 投递 endpoint 动作：

- 创建或获取 `RemoteEndpointClient`。
- 对 subscribe action 调用 `client.EnqueueSubscribe(...)`。
- 对 unsubscribe action 调用 `client.EnqueueUnsubscribe(...)`。
- 不直接调用 `AddOrUpdateSubscription`、`RemoveSubscription`、`EnsureConnectedAsync`、`SendUnsubscribeAsync`。

### 步骤 4：替换 `WebSocketCommunicationModule.UnSubScribe`

让 `UnSubScribe` 调用 aggregator，按返回的 unified plan 投递 endpoint 动作。

### 步骤 5：删除门面类中的聚合字段和私有方法

从 `WebSocketCommunicationModule` 删除：

- `clientSubscriptionGroups`
- `localSubscriptionIndex`
- `clientSubscriptionLock`
- `GetOrCreateClientSubscriptionGroup`
- `RemoveLocalTokenFromGroups`
- `CreateDistinctGroupKeys`
- `CreateSingleRuleRemoteFilter`
- `AreSameGroupSet`

新增：

```csharp
private readonly ClientSubscriptionAggregator subscriptionAggregator = new();
```

`Dispose` 中改为：

```csharp
subscriptionAggregator.Clear();
```

### 步骤 6：整理空 partial 文件

当前 `WebSocketCommunicationModule.Client.cs` 是空文件。拆分后有两个选择：

- 如果客户端逻辑都放入 `Client/*`，删除空 partial 文件。
- 如果仍希望 partial 分层，则把 `Subscribe` / `UnSubScribe` 的薄编排移动到该文件。

推荐第一种：减少 partial 分散，门面类保留对外接口和生命周期即可。

## 15. 最小实现草图

下面是聚合管理器的大致形状：

```csharp
internal sealed class ClientSubscriptionAggregator
{
    private readonly Dictionary<ClientSubscriptionGroupKey, ClientSubscriptionGroup> groups = new();
    private readonly Dictionary<Guid, LocalSubscriptionBinding> localIndex = new();
    private readonly object syncRoot = new();

    public ClientSubscriptionPlan Subscribe(Token token, EventFilter filter)
    {
        lock (syncRoot)
        {
            // 1. validate token/filter/host/source/type
            // 2. parse endpoint
            // 3. build distinct group keys
            // 4. remove stale group references
            // 5. create missing groups, single-rule remote filters, and subscribe actions
            // 6. update localIndex
            // 7. return plan
        }
    }

    public ClientSubscriptionPlan Unsubscribe(Token token)
    {
        lock (syncRoot)
        {
            // 1. remove local binding
            // 2. remove local token from groups
            // 3. create unsubscribe actions for empty groups
            // 4. return plan
        }
    }

    public void Clear()
    {
        lock (syncRoot)
        {
            groups.Clear();
            localIndex.Clear();
        }
    }
}
```

endpoint client 动作队列的最小形状：

```csharp
internal readonly record struct RemoteEndpointAction(
    RemoteEndpointActionKind Kind,
    Guid MasterTokenId,
    EventFilter? RemoteFilter);

internal enum RemoteEndpointActionKind
{
    Subscribe,
    Unsubscribe
}

public void EnqueueSubscribe(Guid masterTokenId, EventFilter remoteFilter)
{
    if (!actionQueue.Writer.TryWrite(
            new RemoteEndpointAction(RemoteEndpointActionKind.Subscribe, masterTokenId, remoteFilter)))
    {
        logger.Warn($"WebSocket subscribe action enqueue failed: {masterTokenId}");
    }
}

public void EnqueueUnsubscribe(Guid masterTokenId)
{
    if (!actionQueue.Writer.TryWrite(
            new RemoteEndpointAction(RemoteEndpointActionKind.Unsubscribe, masterTokenId, null)))
    {
        logger.Warn($"WebSocket unsubscribe action enqueue failed: {masterTokenId}");
    }
}
```

注意：真实实现仍可继续使用 `ConcurrentDictionary`，但如果所有聚合状态读写都受同一个 `syncRoot` 保护，普通 `Dictionary` 更简单。若为了最小改动，可以先保留当前 `ConcurrentDictionary`。

## 16. 评审问题修订

基于并发、异常一致性和性能风险复盘，原方案需要修改。大方向仍然成立：聚合器只维护状态，门面和 endpoint client 执行动作。但必须补充以下生产约束。

### 16.1 必须修订：Plan 动作乱序风险

原方案中，`ClientSubscriptionAggregator` 生成 plan 后立即释放锁，再由 `WebSocketCommunicationModule` 执行动作。这个边界本身是对的，因为不应在聚合锁内执行网络动作；但如果没有额外顺序保证，就会出现同一 endpoint 上的动作乱序。

典型风险：

```text
Thread A: Subscribe(token1)   -> Plan A: subscribe(masterTokenX)
Thread B: Unsubscribe(token1) -> Plan B: unsubscribe(masterTokenX)

实际执行顺序可能变成：
  unsubscribe(masterTokenX)
  subscribe(masterTokenX)
```

最终本地聚合器认为 token 已取消，但远端仍保持订阅，形成幽灵订阅。

修订要求：

1. 同一个 `RemoteEndpointKey` 上的 subscribe/unsubscribe 动作必须按 plan 生成顺序串行应用。
2. 串行化范围至少是 endpoint 级别；如果实现成本允许，也可以做到 endpoint + master token 级别。
3. 串行化应放在 `RemoteEndpointClient` 或 endpoint action dispatcher 内，而不是放在 aggregator 锁内。
4. `WebSocketCommunicationModule` 只负责把 plan 投递到对应 endpoint 的动作队列。

推荐实现：

```csharp
internal sealed class RemoteEndpointClient
{
    private readonly Channel<RemoteEndpointAction> actionQueue = Channel.CreateUnbounded<RemoteEndpointAction>();

    public void EnqueueSubscribe(Guid masterTokenId, EventFilter remoteFilter);

    public void EnqueueUnsubscribe(Guid masterTokenId);
}
```

队列消费者按顺序执行：

```text
subscribe action:
  AddOrUpdateSubscription(masterTokenId, remoteFilter)
  EnsureConnectedAsync()
  如果已经 Connected，则 FlushSubscriptionsAsync 会发送 pending subscribe

unsubscribe action:
  RemoveSubscription(masterTokenId)
  SendUnsubscribeAsync(masterTokenId)
  ScheduleIdleReleaseIfStillIdle()
```

这样即使多个线程同时调用 `Subscribe` / `UnSubScribe`，同一 endpoint 上的动作仍然保持因果顺序。

可选增强：

- 每个 action 携带递增 `Sequence`。
- `RemoteEndpointClient` 记录每个 master token 最后一次应用的 sequence。
- 如果发现旧 sequence 动作晚到，直接丢弃。

### 16.2 必须修订：Plan 应用阶段不能留下半提交状态

原方案默认“网络发送失败不回滚本地聚合状态”，这个原则只适用于真正的异步网络失败。因为网络失败可以由 `RemoteEndpointClient` 保留 pending subscription，并在重连后补发。

但同步应用 plan 的阶段必须尽量做到不抛异常。否则会出现：

1. aggregator 已记录本地订阅。
2. `RemoteEndpointClient` 创建或 `AddOrUpdateSubscription` 失败。
3. 外层调用抛异常中断。
4. 下一次 Subscribe 时 aggregator 认为订阅已存在，返回空 plan。
5. 订阅永远无法真正送到远端。

修订要求：

1. 所有可校验的异常必须在进入 aggregator 之前或 aggregator 内部完成校验：
   - token 是否为空。
   - filter 是否为空。
   - filter host 是否合法。
   - source/eventType 是否有效。
   - endpoint 是否可解析。
2. `CreateRemoteEndpointClient` 必须是纯内存构造，不做 DNS、连接、握手或其他 IO。
3. `RemoteEndpointClient.AddOrUpdateSubscription` 必须是纯内存操作，原则上不抛业务异常。
4. 真正可能失败的 IO 只能发生在后台 `EnsureConnectedAsync`、发送队列或 receive loop 中。
5. 如果同步应用 plan 仍发生意外异常，门面类必须记录错误，并主动调用 aggregator 的补偿方法撤销本次 plan。

可选补偿接口：

```csharp
internal void Rollback(ClientSubscriptionPlan plan);
```

第一版更推荐通过“同步应用零 IO、零可预期异常”来避免补偿复杂度。

### 16.3 必须修订：明确 connected 状态下的新订阅发送语义

原方案伪代码写的是：

```csharp
client.AddOrUpdateSubscription(action.MasterTokenId, action.RemoteFilter);
_ = ObserveBackgroundTask(client.EnsureConnectedAsync());
```

这个写法依赖当前 `EnsureConnectedAsync` 的行为：当 socket 已经 open 且状态为 `Connected` 时，它会调用 `FlushSubscriptionsAsync()`。当前代码确实如此，因此现有实现能发送新增 pending 订阅。

但文档必须把这个行为写成契约，而不是隐式假设。

修订后的边界：

- `AddOrUpdateSubscription` 只负责把 subscription 写入 pending 表。
- `EnsureConnectedAsync` 必须保证：
  - 未连接时执行连接、握手和 flush。
  - 已连接时执行一次 `FlushSubscriptionsAsync`。
- 如果未来将 `EnsureConnectedAsync` 改成“已连接直接返回”，必须新增显式方法：

```csharp
public Task FlushSubscriptionsIfConnectedAsync();
```

或：

```csharp
public void EnqueueSubscribe(Guid masterTokenId, EventFilter remoteFilter);
```

推荐以后者为准，让 endpoint action queue 统一处理顺序和发送触发。

### 16.4 应修订：按需 Clone，降低热路径分配

原方案要求 Subscribe 一开始就 clone `EventFilter`。这最安全，但在大量重复订阅同一 group 的场景中会产生不必要分配。

修订建议：

1. 先基于原始 filter 做只读校验和 group key 计算。
2. 如果本地 token 已存在且 group 集合完全相同，不 clone，直接返回空 plan。
3. 如果 group 已存在，只增加本地 token 引用，不 clone remote filter。
4. 只有创建新的 `ClientSubscriptionGroup` 时，才创建单规则 `RemoteFilter`。
5. `ClientSubscriptionGroup.RemoteFilter` 创建后不再被外部修改。

注意：如果需要保存原始 filter 的完整副本，则仍要 clone；但当前聚合模型只需要保存单规则 remote filter，因此无需对每次 Subscribe 做完整深拷贝。

### 16.5 可优化：Plan/Action 分配

原方案使用 class DTO，更易读、易测试。若订阅变更不是高频热路径，可以保留 class，优先保证正确性。

如果实际业务存在高频订阅/取消，建议调整为：

```csharp
internal readonly record struct ClientRemoteSubscribeAction(
    RemoteEndpointKey Endpoint,
    Guid MasterTokenId,
    EventFilter RemoteFilter);

internal readonly record struct ClientRemoteUnsubscribeAction(
    RemoteEndpointKey Endpoint,
    Guid MasterTokenId);
```

Plan 可以继续使用 class，因为它承载列表；但 action 建议用 `readonly record struct`。如果大多数 plan 只有一个 action，可以再做单 action 快路径。第一版不建议过早引入 `ObjectPool`，否则会增加生命周期和测试复杂度。

### 16.6 必须修订：Endpoint 元数据清理

如果 aggregator 后续引入 endpoint 级索引，例如：

```csharp
Dictionary<RemoteEndpointKey, EndpointSubscriptionState>
```

则取消最后一个 group 时必须清理 endpoint 空壳。

修订要求：

1. 移除最后一个本地 token 后，必须删除空的 `ClientSubscriptionGroup`。
2. 如果存在 endpoint 级字典，endpoint 下 group count 为 0 时必须删除 endpoint key。
3. `HasLocalSubscriptions(endpoint)` 不能因为空字典、空列表残留而返回错误结果。
4. `Clear()` 必须清空所有 group、local index 和 endpoint index。

当前最小方案只使用：

```csharp
Dictionary<ClientSubscriptionGroupKey, ClientSubscriptionGroup> groups;
Dictionary<Guid, LocalSubscriptionBinding> localIndex;
```

在这种结构下，只要 empty group 被 remove，就不会留下 endpoint 空壳。

### 16.7 必须明确：`LocalSubscriptionBinding` 保存完整 GroupKey

更新订阅 diff 依赖本地 token 的历史绑定。`LocalSubscriptionBinding` 必须保存上一次订阅绑定的完整 group key 集合：

```csharp
internal sealed class LocalSubscriptionBinding
{
    public Guid LocalTokenId { get; init; }

    public RemoteEndpointKey Endpoint { get; init; }

    public ClientSubscriptionGroupKey[] GroupKeys { get; init; } = [];

    public Guid[] MasterTokenIds { get; init; } = [];
}
```

其中 `GroupKeys` 是计算新增、保留、删除 group 的依据；`MasterTokenIds` 只用于调试、查询或必要时快速定位，不应替代 group key diff。

## 17. 修订后推荐实现形态

修订后，最推荐的协作模型是：

```text
WebSocketCommunicationModule.Subscribe
  -> subscriptionAggregator.Subscribe(...)
  -> 得到 endpoint action plan
  -> endpointClient.Enqueue(plan actions)

RemoteEndpointClient action loop
  -> 按 endpoint 内顺序应用 Add/Remove
  -> Add 后触发 EnsureConnected/Flush
  -> Remove 后触发 SendUnsubscribe/IdleRelease
```

也就是说，aggregator 仍然不执行副作用，但副作用不再由多个调用线程直接执行，而是由每个 endpoint client 的动作队列串行执行。

如果第一版不想引入 `Channel`，最低限度也应在 `WebSocketCommunicationModule` 增加 endpoint 级锁：

```csharp
private readonly ConcurrentDictionary<RemoteEndpointKey, object> endpointActionLocks = new();
```

应用 plan 时：

```csharp
var endpointLock = endpointActionLocks.GetOrAdd(action.Endpoint, _ => new object());
lock (endpointLock)
{
    // Add/Remove + EnsureConnected/SendUnsubscribe must preserve order.
}
```

这个方案比队列简单，但要注意不能在 lock 内同步等待异步网络动作。它只能保护纯内存状态应用和异步任务投递顺序；长期仍建议迁移到 endpoint action queue。

## 18. 是否有必要修改

有必要修改，而且至少需要修改文档和实现约束。分级如下：

| 问题 | 是否必须修改 | 原因 |
| --- | --- | --- |
| 同 endpoint 动作乱序 | 必须 | 会造成幽灵订阅，属于正确性问题 |
| Plan 应用阶段同步异常 | 必须 | 会造成 aggregator 已提交但 client 未注册的半提交状态 |
| connected 状态下新增订阅发送语义 | 必须 | 当前依赖隐式行为，后续维护容易改坏 |
| Endpoint 空壳清理 | 必须 | 一旦引入 endpoint 索引，会造成内存残留和 idle 判断错误 |
| `LocalSubscriptionBinding.GroupKeys` 明确化 | 必须 | 订阅 diff 的基础数据 |
| action DTO 改 struct | 建议 | 高频场景有收益，但不是第一优先级 |
| ObjectPool/List 复用 | 暂不建议第一版做 | 会提高复杂度，除非性能测试证明必要 |
| 按需 clone | 建议 | 可减少重复订阅场景分配，且实现成本不高 |

因此，原拆分方案应从“Aggregator 生成 Plan，Module 直接执行 Plan”修订为“Aggregator 生成 Plan，Module 将 Plan 投递到 endpoint client 的顺序动作队列”。这是保证职责分离和并发正确性同时成立的关键补丁。

## 19. 结论

抽出 `ClientSubscriptionAggregator` 后，`WebSocketCommunicationModule` 会回到更合适的 facade 角色：接收 Core 调用、调用聚合管理器生成动作、把动作应用到远端连接、转发事件回调。

这个拆分不会改变协议，也不改变 `RemoteEndpointClient` 的连接状态机。它的收益主要是：

- 降低 `WebSocketCommunicationModule` 复杂度。
- 让客户端订阅聚合算法可以独立测试。
- 减少后续修改订阅聚合规则时对连接生命周期代码的影响。
- 为后续继续拆分 `RemoteEndpointClient` 打下边界基础。
