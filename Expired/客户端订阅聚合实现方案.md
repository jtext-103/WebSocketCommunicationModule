# WSCM 客户端订阅聚合实现方案

本文按当前 `WebSocketCommunicationModule` 代码结构给出客户端订阅聚合方案。修订后的核心原则是：

```text
只要客户端收到远程事件后仍然进入本地 EventHub 全局广播，
客户端远程订阅聚合粒度就必须与本地广播粒度一致：
endpoint + Source + EventType。
```

因此，本方案不再按“完整 EventFilter”聚合，而是把 `EventFilter.SourcesAndTypes` 拆成多个单条远程订阅组。

## 1. 背景与目标

当前客户端订阅入口在：

- `WebSocketCommunicationModule/WebSocketCommunicationModule.cs`
- `Subscribe(Token token, EventFilter filter)`
- `UnSubScribe(Token token)`

当前行为是：

```text
每个本地 token.Id
  -> connection.Filters[token.Id] = filter
  -> subscriptions[token.Id] = SubscriptionEntry
  -> FlushSubscriptionsAsync 发送 SubscribeMessage(token.Id, filter)
```

当多个本地 token 订阅相同或相交的远程事件时，客户端会向服务端发送多次 `SubscribeMessage`。服务端虽然已经做了本地 EventHub 聚合，但仍会把这些远程 token 当成多个 remote subscriber。一次业务事件可能返回多条 `RemoteEventMessage`，客户端每收到一条又进入一次本地 EventHub 广播，最终导致重复触发。

目标：

1. 相同 `endpoint + Source + EventType` 的多个本地 token，只向服务端发送一次真实远程订阅。
2. 一个远程事件返回后，客户端仍然只进入一次本地 EventHub 广播。
3. 本地 EventHub 继续按 `Source/EventType` 匹配，触发所有本地订阅者。
4. 不修改 `SubscribeMessage`、`UnsubscribeMessage`、`RemoteEventMessage` 的 wire protocol。
5. 保留现有心跳、重连、重订阅、空闲释放连接逻辑。

最终效果：

```text
tokenA 订阅 /thing/a Changed
tokenB 订阅 /thing/a Changed + /thing/b Changed

客户端拆分聚合：
  groupA = endpoint + /thing/a Changed
  groupB = endpoint + /thing/b Changed

远程只发送：
  Subscribe(MasterA, /thing/a Changed)
  Subscribe(MasterB, /thing/b Changed)

服务端发生 /thing/a Changed：
  只返回 RemoteEvent(MasterA, EventArg)

客户端：
  本地 EventHub 广播一次
  tokenA、tokenB 各触发一次
```

## 2. 必要修改项

以下修改是必须做的，否则保留本地全局广播时仍会存在交集 filter 重复触发风险。

### 2.1 客户端聚合粒度必须拆到 Source/EventType

不要以完整 `EventFilter` 作为 group key。

必须改为：

```text
ClientSubscriptionGroupKey =
  RemoteEndpointKey
  + Source
  + EventType
```

原因：

- 客户端本地 EventHub 是按 `Source/EventType` 广播。
- 如果远程按完整 filter 聚合，`[A]`、`[A,B]`、`[A,C]` 会形成三个远程订阅。
- 服务端发生 `A` 时会返回三条远程事件。
- 客户端三次全局广播后，本地订阅者仍会重复触发。
- 当前 WebSocketCM 不使用 `PerformanceLevel` 字段，所有远程事件统一使用完整 `EventArg` / full sample 推送。

### 2.2 PerformanceLevel 当前必须忽略

当前 WebSocketCM 不使用 `EventFilter.PerformanceLevel` 做传输优化，也不走低开销 object payload 分支。无论订阅方传入什么 `PerformanceLevel`，WebSocketCM 都统一按完整字段推送远程事件：

```text
RemoteEventMessage.EventArg = 完整 EventArg
```

注意：

- `PerformanceLevel` 不参与 group 身份。
- `PerformanceLevel` 不参与 group 状态。
- `PerformanceLevel` 不触发重新订阅。
- `RemoteFilter.PerformanceLevel` 可以固定为默认值 `0`，或沿用创建单条 filter 时的默认值；语义上应被忽略。
- 如果收到非 0 的 `PerformanceLevel`，当前 WebSocketCM 应增加提示/日志，明确说明不支持 `PerformanceLevel` 字段，并继续按完整 `EventArg` / full sample 推送处理。
- 后续如果重新启用低开销模式，需要另开设计，不应混入当前客户端聚合方案。

### 2.3 Subscribe 必须拆分 SourcesAndTypes

`Subscribe(token, filter)` 收到一个包含多条 `SourcesAndTypes` 的 filter 时，必须遍历每一条规则，创建或复用对应的客户端聚合组。

伪流程：

```text
Subscribe(token, filter)
  -> endpoint = RemoteEndpointKey.Parse(filter.Host)
  -> 如果 filter.PerformanceLevel != 0，记录提示：当前 WebSocketCM 不支持 PerformanceLevel 字段，将按 full sample 推送处理
  -> distinct rules = filter.SourcesAndTypes 按 Source/EventType 去重
  -> foreach rule:
       key = endpoint + rule.Source + rule.EventType
       找到或创建 ClientSubscriptionGroup
       把本地 token.Id 加入 group.LocalTokenIds
       如果 group 是新建的：
          创建只包含该 rule 的 RemoteFilter
          RemoteFilter.PerformanceLevel = 0 或保持默认值
          connection.Filters[MasterTokenId] = RemoteFilter
          subscriptions[MasterTokenId] = SubscriptionEntry
          触发 EnsureConnectedAsync(connection)
  -> localSubscriptionIndex[token.Id] = 该 token 参与的所有 group key/master token
```

### 2.4 RemoteFilter 必须是单条规则 filter

每个客户端聚合组发给服务端的 `SubscribeMessage.Filter` 必须只包含一条 `Source/EventType`。

示例：

```text
原始本地 filter:
  Host = ws://server/cfet2/event/v2
  SourcesAndTypes:
    /thing/a Changed
    /thing/b Changed

拆分后远程订阅:
  Subscribe(MasterA, filter: /thing/a Changed)
  Subscribe(MasterB, filter: /thing/b Changed)
```

这样服务端发生 `/thing/a Changed` 时，只会命中 `MasterA`，客户端只广播一次。

### 2.5 LocalSubscriptionBinding 必须支持一个本地 token 对应多个 group

旧设计里一个本地 token 只对应一个 group：

```csharp
public Guid MasterTokenId { get; init; }
public ClientSubscriptionGroupKey GroupKey { get; init; }
```

修订后，一个本地 token 可能来自多条 `SourcesAndTypes`，因此必须支持多个 group：

```csharp
internal sealed class LocalSubscriptionBinding
{
    public Guid LocalTokenId { get; init; }

    public RemoteEndpointKey Endpoint { get; init; }

    public ClientSubscriptionGroupKey[] GroupKeys { get; init; } = [];

    public Guid[] MasterTokenIds { get; init; } = [];
}
```

### 2.6 UnSubScribe 必须从所有 group 中移除本地 token

`UnSubScribe(token)` 不再只处理一个远程 token，而是：

```text
localSubscriptionIndex[token.Id]
  -> 找到该本地 token 参与的所有 group
  -> 从每个 group.LocalTokenIds 移除 token.Id
  -> 如果某个 group 已空：
       移除 clientSubscriptionGroups[groupKey]
       移除 subscriptions[MasterTokenId]
       移除 connection.Filters[MasterTokenId]
       发送 Unsubscribe(MasterTokenId)
```

注意：

- 只有 group 为空时才发送远程退订。
- 远程退订必须使用 `MasterTokenId`。
- 不能使用本地 `token.Id` 发送远程退订。

### 2.7 connection.Filters 与 subscriptions 只保存 MasterTokenId

修改后：

- `RemoteConnection.Filters` 的 key 是 `MasterTokenId`。
- `subscriptions` 的 key 是 `MasterTokenId`。
- 本地 `token.Id` 只存在于 `localSubscriptionIndex` 和 `ClientSubscriptionGroup.LocalTokenIds`。

这样现有 `FlushSubscriptionsAsync`、`HandleSubscribeAck`、`ResetSubscriptionsForReconnect` 大体可以继续复用，只是它们处理的是聚合后的远程订阅。

### 2.8 必须补交集 Filter 测试

必须新增测试：

```text
token1 订阅 [A]
token2 订阅 [A, B]
服务端发生 A
```

断言：

- 客户端只应收到/广播一次 A 事件。
- 本地回调总数应为 2：token1 一次，token2 一次。
- 不能出现 4 次或更多。

这是本方案是否正确的核心验收测试。

## 3. 可选修改项

以下修改不是打通聚合闭环的最低要求，但建议第一版一并纳入，能减少边界行为和后续返工。

### 3.1 RemoteEvent stale token 防御

`HandleRemoteEvent` 可以增加防御性判断：

```csharp
if (message.TokenId.HasValue &&
    !subscriptions.ContainsKey(message.TokenId.Value))
{
    return;
}
```

语义：

- 如果远程事件带 `TokenId`，且该 `MasterTokenId` 已经不存在，说明对应 group 已取消，直接丢弃。
- 如果 `TokenId` 为空，为兼容旧服务端，可以继续广播。

收益：

- 取消订阅后的在途消息不会再次进入本地 EventHub。

### 3.2 同一 token 重复订阅相同 group 幂等

如果同一个本地 token 重复订阅完全相同的规则集合，推荐直接返回，不产生远程 unsubscribe/subscribe 抖动。

判断方式：

```text
old binding 的 GroupKeys 集合 == new GroupKeys 集合
  -> 幂等 return
```

如果集合不同，才执行迁移：

```text
旧 group 移除 token
新 group 添加 token
空 group 发送远程 Unsubscribe
新 group 发送远程 Subscribe
```

如果 group 集合相同但只有 `PerformanceLevel` 变化，当前 WebSocketCM 仍视为幂等，不重发订阅。

### 3.3 SourcesAndTypes 去重

同一个 filter 内可能出现重复规则：

```text
/thing/a Changed
/thing/a Changed
```

Subscribe 时必须先按：

```text
Source + EventType
```

去重，避免同一个本地 token 对同一个 group 重复操作。

`PerformanceLevel` 不参与去重，也不影响 group 生成。

如果 `filter.PerformanceLevel != 0`，应记录一次清晰提示，例如：

```text
WebSocketCM does not support PerformanceLevel; full EventArg payload will be used.
```

提示不能阻断订阅，除非后续产品策略明确要求非 0 值直接拒绝。

### 3.4 锁内禁止等待网络 IO

`clientSubscriptionLock` 内只能修改内存状态，不能同步等待网络发送。

如果在锁内判断需要发送远程 unsubscribe，仍应使用当前模式：

```csharp
_ = ObserveBackgroundTask(
    SendUnsubscribeAndScheduleReleaseIfIdleAsync(...));
```

不能在锁内 `await` 或同步阻塞，否则容易阻塞其他 Subscribe/UnSubScribe。

### 3.5 孤儿本地 token 的生命周期管理

如果上层 UI/组件忘记调用 `UnSubScribe`，本地 token 会留在 group 中，使远程订阅长期存在。

第一版可接受：

- 依赖调用方正确释放 token。
- `WebSocketCommunicationModule.Dispose()` 统一清空索引和连接。

后续可考虑：

- 由上层作用域批量清理本地 token。
- 或为 token 生命周期增加统一 dispose hook。

### 3.6 EventId 去重不作为第一版方案

不建议第一版引入“事件级 EventId 去重缓存”。

原因：

- 当前问题可以通过 Source/EventType 最小粒度聚合解决。
- EventId 需要业务事件全局唯一标识，当前协议和 `EventArg` 未必稳定提供。
- 缓存会引入时间窗口、内存和误判复杂度。

只有未来存在正则/模式重叠导致无法靠精确 key 聚合解决时，再考虑事件级去重。

## 4. 新增模型

建议新增目录：

```text
WebSocketCommunicationModule/Connections/ClientAggregation/
```

也可以先放在 `Connections` 目录，减少目录层级。

### 4.1 ClientSubscriptionGroupKey

```csharp
internal readonly record struct ClientSubscriptionGroupKey(
    RemoteEndpointKey Endpoint,
    string Source,
    string EventType);
```

说明：

- `Endpoint` 使用当前已有的 `RemoteEndpointKey.Parse(filter.Host)` 结果。
- `Source/EventType` 来自单条 `SourcesAndTypes`。
- `PerformanceLevel` 不进入 key，当前 WebSocketCM 也不使用该字段。
- 如果订阅 filter 携带非 0 `PerformanceLevel`，模块应提示不支持该字段。
- `Host` 不需要单独加入，因为已经由 `Endpoint` 表示。

### 4.2 ClientSubscriptionGroup

```csharp
internal sealed class ClientSubscriptionGroup
{
    public Guid MasterTokenId { get; init; }

    public ClientSubscriptionGroupKey Key { get; init; }

    public RemoteEndpointKey Endpoint { get; init; }

    public EventFilter RemoteFilter { get; init; } = new();

    public ConcurrentDictionary<Guid, byte> LocalTokenIds { get; } = new();

    public DateTime CreatedAtUtc { get; init; }
}
```

说明：

- `MasterTokenId` 是真正发给服务端的 token。
- `RemoteFilter` 必须是只包含该 group 单条 `Source/EventType` 的 filter。
- `LocalTokenIds` 保存所有复用该远程订阅的本地 token。

### 4.3 LocalSubscriptionBinding

```csharp
internal sealed class LocalSubscriptionBinding
{
    public Guid LocalTokenId { get; init; }

    public RemoteEndpointKey Endpoint { get; init; }

    public ClientSubscriptionGroupKey[] GroupKeys { get; init; } = [];

    public Guid[] MasterTokenIds { get; init; } = [];
}
```

说明：

- 一个本地 token 可能对应多个 group。
- `GroupKeys` 用于退订时快速从 group 中移除本地 token。
- `MasterTokenIds` 用于测试、日志或诊断。

## 5. 新增字段

在 `WebSocketCommunicationModule.cs` 中新增：

```csharp
private readonly ConcurrentDictionary<ClientSubscriptionGroupKey, ClientSubscriptionGroup> clientSubscriptionGroups = new();
private readonly ConcurrentDictionary<Guid, LocalSubscriptionBinding> localSubscriptionIndex = new();
private readonly object clientSubscriptionLock = new();
```

第一版用单锁保护：

- group 创建和删除。
- local token 与 group 的绑定迁移。
- `subscriptions` 和 `connection.Filters` 的同步更新。

## 6. Subscribe 流程

推荐流程：

```text
Subscribe(token, filter)
  -> 校验 token/filter/disposed/Host
  -> clonedFilter = new EventFilter(filter)
  -> endpoint = RemoteEndpointKey.Parse(clonedFilter.Host)
  -> rules = clonedFilter.SourcesAndTypes 按 Source/EventType 去重
  -> newGroupKeys = rules 映射成 ClientSubscriptionGroupKey[]
  -> lock(clientSubscriptionLock)
       如果 token 已经绑定到相同 group 集合：
          return
       否则先从旧 group 集合移除 token
       对每个 newGroupKey：
          找到或创建 ClientSubscriptionGroup
          group.LocalTokenIds[token.Id] = 0
          如果 group 新建：
             connection.Filters[group.MasterTokenId] = group.RemoteFilter
             subscriptions[group.MasterTokenId] = Pending SubscriptionEntry
       localSubscriptionIndex[token.Id] = new binding
  -> 对所有新建 group 对应的 connection 调用 EnsureConnectedAsync
```

创建单条 `RemoteFilter` 的伪代码：

```csharp
private static EventFilter CreateSingleRuleRemoteFilter(
    EventFilter sourceFilter,
    SourceAndTypeFilter rule,
    string host)
{
    var remoteFilter = new EventFilter(sourceFilter)
    {
        Host = host,
        PerformanceLevel = 0,
    };

    remoteFilter.SourcesAndTypes.Clear();
    remoteFilter.SourcesAndTypes.Add(rule);
    return remoteFilter;
}
```

实际类型名以 CFET2 Core 中 `SourcesAndTypes` 元素类型为准。

## 7. UnSubScribe 流程

推荐流程：

```text
UnSubScribe(token)
  -> token null 直接 return
  -> lock(clientSubscriptionLock)
       localSubscriptionIndex.TryRemove(token.Id, out binding)
       foreach groupKey in binding.GroupKeys:
          group.LocalTokenIds.TryRemove(token.Id)
          如果 group 为空：
             clientSubscriptionGroups.TryRemove(groupKey)
             subscriptions.TryRemove(group.MasterTokenId)
             connection.Filters.TryRemove(group.MasterTokenId)
             fire-and-forget SendUnsubscribe(MasterTokenId)
             如果 connection.Filters.IsEmpty，走空闲释放逻辑
```

注意：

- 同一个 token 的多条 group 必须全部清理。
- group 非空时不能发送远程退订。
- group 空时只退订一次。

## 8. FlushSubscriptionsAsync 与重连

`FlushSubscriptionsAsync` 当前遍历 `connection.Filters.Keys` 并查 `subscriptions[tokenId]`。

客户端聚合后仍可复用：

- `connection.Filters.Keys` 是 `MasterTokenId` 集合。
- `subscriptions[MasterTokenId]` 是远程订阅状态。
- `SubscribeAckMessage.TokenId` 也是 `MasterTokenId`。

重连链路也保持：

```text
ResetSubscriptionsForReconnect(connection)
  -> 重置 MasterTokenId 对应 SubscriptionEntry
EnsureConnectedAsync(connection)
  -> FlushSubscriptionsAsync(connection)
  -> 按 group 重发 Subscribe(MasterTokenId, RemoteFilter)
```

## 9. RemoteEvent 返回流程

保留本地 EventHub 广播：

```text
RemoteEvent(MasterTokenId, EventArg)
  -> HandleRemoteEvent
  -> RaiseRemoteEvent
  -> InvokeEventCallback
  -> 本地 EventHub 按 Source/EventType 广播
```

建议加入可选 stale token 判断：

```csharp
if (message.TokenId.HasValue &&
    !subscriptions.ContainsKey(message.TokenId.Value))
{
    return;
}
```

不做：

```text
RemoteEvent.TokenId -> 本地 token 精准回调
```

原因：

- 当前 `IEventCommunicationModule.RegisterEventCallback(Action<EventArg>)` 没有 token 级 callback。
- 客户端按 Source/EventType 拆分聚合后，远程同一事件只回来一条，本地全局广播不会重复。

## 10. Dispose 调整

`Dispose()` 需要清理新增索引：

```csharp
clientSubscriptionGroups.Clear();
localSubscriptionIndex.Clear();
```

Dispose 中不需要逐个发送远程 unsubscribe，因为连接即将释放。

## 11. 实现步骤

建议按以下顺序提交：

1. 新增客户端聚合模型：
   - `ClientSubscriptionGroupKey`
   - `ClientSubscriptionGroup`
   - `LocalSubscriptionBinding`
2. 新增聚合字段：
   - `clientSubscriptionGroups`
   - `localSubscriptionIndex`
   - `clientSubscriptionLock`
3. 新增 rule 拆分辅助：
   - 从 `EventFilter.SourcesAndTypes` 生成去重后的 `ClientSubscriptionGroupKey[]`
   - 从原 filter 创建单条 rule 的 `RemoteFilter`
4. 修改 `Subscribe(...)`：
   - 按单条 `Source/EventType` 建 group。
   - 只有新 group 创建时才写入 `connection.Filters/subscriptions`。
   - 同一 token 重复订阅相同 group 集合时幂等返回。
5. 修改 `UnSubScribe(...)`：
   - 从该 token 对应的所有 group 中移除。
   - 最后一个本地 token 离开 group 时发送 `Unsubscribe(MasterTokenId)`。
6. 修改 `Dispose()`：
   - 清空客户端聚合索引。
7. 可选增强 `HandleRemoteEvent(...)`：
   - `TokenId` 存在且 group 已不存在时丢弃在途事件。
8. 补充测试。
9. 跑完整 `dotnet test`。

## 12. 测试方案

建议新增测试文件：

```text
TestCode/WebSocketClientAggregationTests.cs
```

### 12.1 相同单条规则只发送一次 Subscribe

场景：

```text
token1 订阅 endpoint + /thing/status Changed
token2 订阅 endpoint + /thing/status Changed
```

断言：

- 服务端只收到 1 条 `SubscribeMessage`。
- 该消息的 `TokenId` 不是 `token1.Id`，也不是 `token2.Id`。
- 客户端内部 `subscriptions.Count == 1`。
- 客户端内部 `connection.Filters.Count == 1`。
- 客户端内部 `localSubscriptionIndex.Count == 2`。
- 客户端内部 `clientSubscriptionGroups.Count == 1`。

### 12.2 交集 Filter 不导致本地广播风暴

核心验收测试。

场景：

```text
token1 订阅 [/thing/a Changed]
token2 订阅 [/thing/a Changed, /thing/b Changed]
服务端针对 /thing/a Changed 只返回一条 RemoteEvent
```

断言：

- 客户端只对 `/thing/a Changed` 广播一次。
- token1 回调一次。
- token2 回调一次。
- 总回调次数为 2，不是 4。

### 12.3 多条 SourcesAndTypes 拆成多个远程 Subscribe

场景：

```text
token1 订阅 [/thing/a Changed, /thing/b Changed]
```

断言：

- 服务端收到 2 条 `SubscribeMessage`。
- 每条 `SubscribeMessage.Filter.SourcesAndTypes.Count == 1`。
- 客户端 `clientSubscriptionGroups.Count == 2`。
- `localSubscriptionIndex[token1.Id].GroupKeys.Length == 2`。

### 12.4 不同 source 不聚合

场景：

```text
token1 订阅 /thing/a Changed
token2 订阅 /thing/b Changed
```

断言：

- 服务端收到 2 条 `SubscribeMessage`。
- 客户端 `subscriptions.Count == 2`。
- 客户端 `clientSubscriptionGroups.Count == 2`。

### 12.5 不同 eventType 不聚合

场景：

```text
token1 订阅 /thing/status Changed
token2 订阅 /thing/status Deleted
```

断言：

- 服务端收到 2 条 `SubscribeMessage`。
- 两个 group 独立。

### 12.6 不同 endpoint 不聚合

场景：

```text
token1 订阅 endpointA + /thing/status Changed
token2 订阅 endpointB + /thing/status Changed
```

断言：

- 两个服务端各收到 1 条 `SubscribeMessage`。
- 客户端有 2 个 `RemoteConnection`。
- 客户端有 2 个 group。

### 12.7 相同 Source/EventType 不同 PerformanceLevel 仍然聚合且不重发

场景：

```text
token1 订阅 /thing/status Changed, PerformanceLevel = 0
token2 订阅 /thing/status Changed, PerformanceLevel = 1
```

断言：

- 客户端只有 1 个 group。
- 服务端只保留 1 个远程订阅 token。
- `ClientSubscriptionGroupKey` 不包含 `PerformanceLevel`。
- 第二个 token 加入时不因为 `PerformanceLevel` 不同而重发订阅。
- 发出的 `SubscribeMessage.Filter.PerformanceLevel` 固定为默认值 `0`，或语义上被服务端忽略。
- 对非 0 `PerformanceLevel` 产生“不支持 PerformanceLevel 字段，将使用 full sample 推送”的提示/日志。

### 12.8 非 0 PerformanceLevel 应提示不支持但不阻断订阅

场景：

```text
token1 订阅 /thing/status Changed, PerformanceLevel = 1
```

断言：

- 订阅仍然成功。
- 服务端仍收到正常 `SubscribeMessage`。
- 客户端记录/提示当前 WebSocketCM 不支持 `PerformanceLevel` 字段。
- 远程事件仍按完整 `EventArg` / full sample 处理。

### 12.9 取消一个本地 token 不发送远程 Unsubscribe

场景：

```text
token1、token2 订阅相同单条规则
token1 UnSubScribe
```

断言：

- 服务端没有收到 `UnsubscribeMessage`。
- group 仍存在。
- group.LocalTokenIds 只剩 token2。
- `connection.Filters.Count == 1`。

### 12.10 取消最后一个本地 token 才发送远程 Unsubscribe

场景：

```text
token1、token2 订阅相同单条规则
token1 UnSubScribe
token2 UnSubScribe
```

断言：

- 服务端最终只收到 1 条 `UnsubscribeMessage`。
- `UnsubscribeMessage.TokenId == MasterTokenId`。
- 客户端 `clientSubscriptionGroups.Count == 0`。
- 客户端 `localSubscriptionIndex.Count == 0`。
- 客户端 `subscriptions.Count == 0`。
- 客户端 `connection.Filters.Count == 0`。

### 12.11 多规则 token 取消时释放所有 group

场景：

```text
token1 订阅 [/thing/a Changed, /thing/b Changed]
token1 UnSubScribe
```

断言：

- 服务端收到 2 条 `UnsubscribeMessage`。
- 两个 `MasterTokenId` 都被退订。
- 客户端没有残留 group。

### 12.12 重复 SourcesAndTypes 不导致重复 group

场景：

```text
filter.SourcesAndTypes = [/thing/a Changed, /thing/a Changed]
```

断言：

- 创建 1 个 group。
- 服务端收到 1 条 `SubscribeMessage`。

### 12.13 同一 token 重复订阅相同规则集合幂等

场景：

```text
token1 Subscribe([/thing/a Changed, /thing/b Changed])
token1 Subscribe([/thing/b Changed, /thing/a Changed])
```

断言：

- group 数量仍为 2。
- 服务端不产生额外有效 Subscribe/Unsubscribe。
- `localSubscriptionIndex[token1.Id]` 仍对应相同 group 集合。

### 12.14 同一 token 改订不同规则集合

场景：

```text
token1 Subscribe([/thing/a Changed])
token1 Subscribe([/thing/b Changed])
```

断言：

- 旧 group 被释放。
- 服务端收到旧 `MasterTokenId` 的 `UnsubscribeMessage`。
- 服务端收到新 group 的 `SubscribeMessage`。
- 客户端最终只有新 group。

### 12.15 同一 token 相同规则集合但 PerformanceLevel 变化仍幂等

场景：

```text
token1 Subscribe([/thing/a Changed], PerformanceLevel = 0)
token1 Subscribe([/thing/a Changed], PerformanceLevel = 1)
```

断言：

- group key 不变。
- group 数量仍为 1。
- 客户端不重发订阅。
- `localSubscriptionIndex[token1.Id]` 仍对应相同 group 集合。

### 12.16 重连后只按 group 重订阅

场景：

```text
token1、token2 订阅相同规则
服务端关闭第一次连接
客户端重连
```

断言：

- 第一次连接收到 1 条 `SubscribeMessage`。
- 第二次连接也只收到 1 条 `SubscribeMessage`。
- 重连后订阅状态恢复 Active。
- 不会按 token1/token2 发两次重订阅。

### 12.17 取消后在途 RemoteEvent 可选丢弃

如果实现了 `HandleRemoteEvent` stale token 判断，补充：

场景：

```text
token1 Subscribe(filter)
服务端拿到 MasterTokenId
token1 UnSubScribe
服务端再发送 RemoteEvent(MasterTokenId, eventArg)
```

断言：

- 客户端不再触发本地回调。

### 12.18 Dispose 清理聚合索引

场景：

```text
token1、token2 订阅相同规则
module.Dispose()
```

断言：

- `clientSubscriptionGroups.Count == 0`。
- `localSubscriptionIndex.Count == 0`。
- `subscriptions.Count == 0`。
- `connections.Count == 0`。

### 12.19 现有测试调整

需要调整或确认：

- `WebSocketSubscriptionPhase4Tests.ConcurrentSubscriptions_ShouldSendOneSubscribePerToken`

客户端聚合后，“每个 token 发一次 Subscribe”不再是正确语义。建议拆成：

1. `DifferentRules_ShouldSendOneSubscribePerGroup`
   - token1 `/thing/a`
   - token2 `/thing/b`
   - 断言 2 条 Subscribe。

2. `SameRule_ShouldSendOneSubscribeForMultipleLocalTokens`
   - token1 `/thing/status`
   - token2 `/thing/status`
   - 断言 1 条 Subscribe。

反射辅助也要调整：

- `subscriptions` key 改为 `MasterTokenId`。
- 本地 token 查状态时，需要先通过 `localSubscriptionIndex` 找到 `MasterTokenIds`。
- 多规则本地 token 可能对应多个远程订阅状态。

## 13. 风险与边界

### 13.1 正则或模式重叠

本方案按精确 `Source + EventType` 聚合，不做正则语义合并。

例如：

```text
/thing/.*
/thing/a
```

会被视为两个不同 group。若服务端对同一个事件同时命中两者，客户端仍可能收到两条远程事件并广播两次。

第一版不建议解决这个问题，因为需要理解 EventHub 完整匹配语义，误合并风险高。后续若必须解决，再考虑 EventId 去重。

### 13.2 PerformanceLevel 当前忽略

`PerformanceLevel` 不允许进入 `ClientSubscriptionGroupKey`，当前 WebSocketCM 也不使用它做传输策略。

原因：

- 它不影响本地 EventHub 的事件匹配身份。
- 当前 WebSocketCM 统一使用完整 `EventArg` / full sample 推送，不走 `PerformanceLevel = 1` 的低开销模式。
- 收到非 0 `PerformanceLevel` 时应提示不支持该字段，但不阻断订阅。
- 如果把它放进 key，同一个 `Source/EventType` 会因为性能级别不同拆成多个远程订阅，服务端同一事件可能返回多条消息，客户端本地全局广播仍会重复。

正确处理方式：

```text
GroupKey = endpoint + Source + EventType
RemoteFilter.PerformanceLevel = 0 或保持默认值
RemoteEventMessage.EventArg = 完整 EventArg
```

### 13.3 本地全局广播保留

本方案明确保留：

```text
RemoteEvent -> 本地 EventHub 按 Source/EventType 广播
```

不做 token 精准回调。因为客户端最小粒度聚合后，正常精确规则不会重复返回同一事件。

## 14. 结论

客户端聚合的必要修改项是：

```text
从“完整 filter 聚合”
改为
“endpoint + Source + EventType 最小粒度聚合”
```

这样才能和“保留客户端本地 EventHub 全局广播”的架构闭环。

`PerformanceLevel` 不进入聚合 key，也不进入当前 WebSocketCM 的聚合状态。当前所有远程事件统一 full sample 推送。

推荐最终形态：

```text
多个本地 token
  -> 按 SourcesAndTypes 拆成多个客户端 group
  -> 每个 group 一个 MasterTokenId
  -> 每个 group 只发一次远程 Subscribe
  -> 服务端每个命中规则只返回一条 RemoteEvent
  -> 客户端本地 EventHub 广播一次
  -> 本地匹配订阅按原有语义触发
```

可选修改项建议第一版一并纳入：

- stale `TokenId` 远程事件丢弃。
- 同一 token 重复订阅相同 group 集合幂等。
- `SourcesAndTypes` 去重。
- 锁内不等待网络 IO。
- 补充孤儿 token 生命周期说明。
